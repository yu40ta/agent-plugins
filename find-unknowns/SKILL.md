# Skill: Find Unknowns

着想: [A Field Guide to Fable: Finding Your Unknowns](https://x.com/trq212) (Thariq, 2026-07-04)。

## コンセプト

- **map** = タスクに渡す指示・プロンプト・context
- **territory** = 実際の作業対象 (codebase・実世界・実制約・ドメイン知識)
- **unknowns** = map と territory の差

作業量が増えるほど Claude は unknowns に遭遇し、推測で判断する回数が増える。推測判断の積み重ねが品質のボトルネックになる。本 skill は着手前〜委譲前にその差を体系的に発見し、解消または既存 skill へ誘導する。

---

## 起動条件

- 手動起動 (/find-unknowns)。自動発火はしない
- **適用場面**:
  - 新領域・不慣れなドメインのタスク開始時
  - 長丁場タスクの計画前
  - 委譲 handover 作成前
  - 長期タスクの出来が悪かったときの振り返り起点

---

### Phase 1: 立ち位置ヒアリング

ユーザーの starting point を AskUserQuestion で収集する。

聞く軸 (3 点):
1. 対象領域の経験・親密度 — 初見 / 触ったことがある / 熟知
2. 思考の現在地 — 何を決めていて何が未決か
3. 「良い」の基準の言語化可否 — できる / 見れば分かる / 分からない

> **目的**: 後の診断で「何を調査するか」「どの象限に振るか」の判断精度を上げる。ヒアリング結果は Phase 2〜3 の全工程に引き通す。

---

### Phase 2: 4 象限診断

4 象限は「map と territory の差」を、ユーザーの自覚の有無 (知っている・自覚している・気づいていない) で切り分けたものである。対象タスクの要素を以下に仕分けし、各象限の処理先を決める。

| 象限 | 定義 | 処理 |
|---|---|---|
| Known Knowns | 指示にすでに書かれていること | 確認のみ (齟齬があれば指摘) |
| Known Unknowns | 未決と自覚している事項 | リスト化 → AskUserQuestion で解消 or 調査タスク化 |
| Unknown Knowns | 見れば分かるが言語化できない基準 | プロトタイプ・複数案比較へ (Phase 4 ルーティング) |
| Unknown Unknowns | 考慮すらしていない領域 | Blind Spot Pass (Phase 3) へ送る |

仕分け結果は会話内に表として出力し、ユーザーと認識を合わせてから Phase 3 に進む。

---

### Phase 3: Blind Spot Pass

Unknown Unknowns を発見するための調査フェーズ。

**手順**:
1. 対象領域 (codebase・ドメイン知識・過去の経緯) を**実際に調査してから**盲点を列挙する。調査なしに一般論の盲点を並べない (推測ではなく実態を確認してから判断する、という基本原則と整合させる)
2. 各盲点に以下を付す:
   - (a) なぜユーザーの盲点になっているか
   - (b) 放置するとどう失敗するか
   - (c) 指示・プロンプトにどう反映すべきか
3. カバーする観点: 「良い」の基準・過去の類似作業・避けるべき落とし穴・質問すべきと気づいていない論点
   - 「避けるべき落とし穴」は、ここでは調査で見つかった盲点の指摘までに留める。失敗/離脱パターンの網羅的な列挙が必要なら Phase 4 で別スキルへ振る

**references 誘導**:
- 言語化困難な要件 (Unknown Knowns) を検出したら、参照物の提供を促す
- 参照物はスクリーンショットより実物 (コード・ファイル・既存成果物) を優先するよう案内する

---

### Phase 4: ルーティングと最終出力

Phase 4 の入力は次の 3 つである: (a) Phase 2 で Unknown Knowns に仕分けた項目、(b) Phase 2 の Known Unknowns のうち AskUserQuestion で解消できなかった項目、(c) Phase 3 の Blind Spot Pass で発見した盲点リスト。これらをルーティング表の「発見した unknowns の型」に照らして振り分ける。各行き先の手順は再掲しない (二重管理禁止)。

**ルーティング表** (行き先は自分の環境にある同種の skill・コマンドに読み替えてよい):

| 発見した unknowns の型 | 行き先の性質 |
|---|---|
| 設計の曖昧さ・未決分岐が残る | 意思決定ツリーの分岐を 1 問ずつ潰す壁打ちインタビュー |
| 失敗・離脱リスクの洗い出しが必要 | 失敗/離脱パターンの仮説列挙と対策設計 |
| 要件が発散・スコープ未定 | ブレインストーミング (`superpowers:brainstorming` 等) |
| 視覚・taste 系 (見れば分かる) | 複数案プロトタイプの作成は実装セッション・下位 tier への委譲に回す。配色・見た目の比較は候補を並べて選ばせる |
| 成果物の理解確認 (実装後) | 対話的な理解度チェック |
| 完了報告前の品質検証 | 独立・敵対的レビュー (`../adversarial-review-loop/SKILL.md`) |

複数行に該当する場合は、タスクの成熟度順に上流から 1 つずつ処理する: 要件が発散していればブレインストーミングを最優先、次に設計前の失敗リスクの洗い出し、計画が固まってから分岐を潰す壁打ちという順で進め、併走させない。

**最終出力 (会話内に 3 点を出す)**:

1. **改善された指示文** — 診断で解消した unknowns を織り込んだプロンプト/指示の書き直し案
2. **残存 unknowns リスト** — 解消できなかったものと、作業中に遭遇したときの判断方針
3. **委譲する場合の Deviations 記録指示** — 引き継ぎ文書を作成する場合、以下を組み込む:
   > 「計画から逸脱が必要になったら保守的選択肢を選び、逸脱内容と理由を引き継ぎ文書の Deviations セクションに記録して続行せよ」

## 出力先

会話内が基本。ファイルとして保存する場合は、プロジェクトの既定の出力先ルールに従う (無ければユーザーに保存先を確認する)。

## 注意事項

- ルーティング先の手順を本 skill に再掲しない
- Blind Spot Pass は調査に基づく。対象を読まずに一般論の盲点を並べない
- 本 skill は診断と誘導まで。実装・執筆はしない
