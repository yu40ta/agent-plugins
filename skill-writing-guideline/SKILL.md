# Skill: Skill Writing Guideline

自作 skill (パス参照型 + SKILL.md 起動型 + modules 型) の記述規範。

**相互参照 (統合しない)**: モデル選定基準・外部スキル取り込みのポリシー・起動条件と発火機構の整合性検証を別途運用している場合はそちらに譲る。本ガイドラインは「skill ファイルの書き方」のみを定める。

---

## 起動条件

- 手動起動。自動発火はしない
- **適用場面**: skill を新規作成する / 既存 skill を内容変更する / skill レビューの判断基準として参照する

---

## 1. 3 形式の使い分け

| 形式 | 配置 | 使いどころ |
|---|---|---|
| **パス参照型** (既定) | `.claude/skills/<domain>/<name>.md` | 手順書・規範・チェックリスト。プロジェクトの指示ファイル (`AGENTS.md` 等) の一覧からポインタで案内し、明示的に Read させて起動する。迷ったらこれ |
| **SKILL.md 起動型** | `.claude/skills/<name>/SKILL.md` (**1 階層直下**) | Skill ツール一覧に載せて名前起動させたいもの、またはスクリプト・テンプレート等の同梱資産があるもの |
| **modules 型** | `.claude/skills/<domain>/<name>/modules/*.md` | skill ではない。親 skill が実行時に Read する参照ファイル (契約データ)。構造は用途に応じて設計する |

> **⚠️ SKILL.md 配置の罠**: `.claude/skills/<domain>/<name>/SKILL.md` のように domain サブディレクトリを挟む 2 階層配置では Skill ツール一覧に登録されない (実測: domain 配下に置いた複数のスキルが全て未出だった)。SKILL.md 型は必ず `.claude/skills/<name>/` 直下に置くこと。

---

## 2. frontmatter 規約

**パス参照型の必須 4 フィールド**:

| フィールド | 規約 |
|---|---|
| `name` | kebab-case・ファイル名 (拡張子除く) と一致 |
| `description` | 「何をするか」+「いつ使うか (トリガー条件)」を 1〜3 文で。手動起動なら「手動起動する」と明記。誇張・宣伝調は書かない |
| `version` | semver。**major = 手順の互換性破壊 / minor = 手順追加 / patch = 表現の実質変更**。体裁のみの機械的変更では上げない |
| `tags` | 配列。先頭に domain (`common` 等) |

**任意フィールド**: `source` (外部由来 skill のみ・出典 URL + ライセンス) / `inspired_by` (着想元の明示)。

**禁止フィールド**:
- `trigger:` — トリガー条件は description に統合する (**根拠**: A/B 実測で「description に置くと起動精度が上がる」を確認済み。二重管理は片方が陳腐化する)
- `model:` — skill には書かない (モデル選定基準を別途運用している場合はそちらに従う)

**SKILL.md 起動型**: agentskills.io の公式スキーマ準拠 (`name` / `description` 必須)。version / tags は強制しない (公式フィールド外のため)。description のトリガー条件記述はパス参照型と同じ規約を適用する。

---

## 3. 見出し・構造規約

- **起動条件は `## 起動条件` に統一**。中身の bullet で「手動 (/command) か自動か」「自動なら発火機構 (hook/settings) はどれか」を書く。**発火機構なしに自動起動を書かない** (発火機構が無い自動起動の記載は運用上の整合性を崩す)
- **手順フロー**: 大ステージ = `### Phase N:` (3〜7 個まで)。Phase 内の細手順は番号付き bullet。`## STEP N` (大文字) は新規で使わない。**参照・規範型** (フローを持たない skill) は `## N.` 連番見出しでよい — フロー型と規範型を混ぜない
- **末尾の定番セクション**: `## 注意事項` (制約・gotcha)。成果物を生む skill は `## 出力先` を必須にし、プロジェクトの出力先ルールと矛盾させない
- **長さの目安**: 150 行以内。300 行を超えるなら modules 分離・参照資料化・skill 分割を検討する

---

## 4. 本文の記述規範

- **バージョン付きモデル名をハードコードしない**: 「Claude Opus 4.8」等のモデル名・フル ID を本文に直書きしない。Co-Authored-By のようなトレイラーは「ハーネスが注入する既定値 (現行セッションのモデル名) に従う」と書く。subagent 委譲の指示はエイリアス tier (haiku / sonnet / opus 等) で書き、判定基準は別途運用しているモデル選定基準に従う
- **@ 参照は実在パスのみ**。ただし gitignore 対象 (PII 系 skill 等) への参照は許可し、**「(PII 系・gitignore 対象・git 外運用)」と注記する** (死リンク検査の誤検知を防ぐ)
- **指示ファイル (AGENTS.md 等) と手順を二重管理しない**: 手順詳細は skill 側に置き、指示ファイル側はポインタ + トリガー 1 行のみ
- **外部由来 skill は verbatim 転記しない**: 独自書き下ろし + `source:` で出典明記
- **Python のサードパーティ依存は `uv run --with` で書く**: `uv run --python 3.13 --with <pkg> <script.py>` の形にする。`pip install` / `pip3 install` を手順に書かない (Homebrew Python 等 PEP 668 準拠の環境では `EXTERNALLY-MANAGED` エラーで失敗し、`--break-system-packages` のような安全装置の無効化は避けるべき)。常設 venv を新設しない

---

## 5. 新規作成・変更時チェックリスト

1. frontmatter 必須 4 フィールド (パス参照型) / 公式スキーマ (SKILL.md 型)
2. description にトリガー条件が入っているか (独自 `trigger:` を作っていないか)
3. `## 起動条件` があり、自動起動記載なら発火機構が実在するか
4. @ 参照先が実在するか (gitignore 対象は注記付きか)
5. モデル名ハードコード・skill 内 `model:` が無いか
6. プロジェクトの skill 一覧・指示ファイルへの登録 (トリガー形式 1 行)
7. 出力先がプロジェクトの出力先ルールと整合するか

---

## 6. 既存ファイルへの適用方針

記述規約を後から変更した場合、既存ファイルへの機械的な一括適用 (起動条件見出し統一・frontmatter 補完・`trigger:` 削除・モデル名ハードコード除去等) は 1 回の一括 PR で行うとよい。体裁のみの変更なら version は上げない。

**本文構造 (Phase/Step 階層・長さ・記述順) は新規作成・内容変更のタイミングで漸進適用する。** 既存の一括再編成はしない。

---

## 注意事項

- `trigger:` フィールドを作ってはいけない (description に統合済みの設計判断)
- `model:` フィールドも skill には書かない (起動セッションのモデルで実行されるため)
- 自動起動を記載する場合は必ず対応する発火機構 (hooks/settings) を同時実装すること。発火機構なしに自動記載すると整合性チェックに引っかかる
