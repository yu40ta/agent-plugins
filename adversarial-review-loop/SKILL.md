# Skill: Adversarial Review Loop

重要成果物 (レビュー・設計提案・アーキテクチャ判断・修正) の完了報告前には、独立・敵対的検証を最低 1 回挟むべきである、という運用規範の実行手順。自己レビューは確証バイアスで検証にならないため、本 skill では独立 subagent を使う。

**既存資産との棲み分け**: 本 skill は、出力前に自分自身で行う軽量な自己反芻 (独立性なし) の上位に位置づけられる、独立 subagent を使った重い検証である。経営・戦略判断に特化した固定レンズの検証や、tiered subagent の一般的な振り分け規約を別途持っている場合は、それらと組み合わせて使ってよい (Phase 2 の subagent dispatch はそうした一般規約に従う)。

---

## 起動条件

- 手動起動。自動発火はしない
- **適用場面**: レビュー・設計提案・アーキテクチャ判断・修正の完了報告前。**実行前の計画承認依頼も対象に含む**: ユーザーに相応の作業負担 (実験・データ収集・複数セッションでの手動作業等) を求める実行計画は、着手の go/no-go をユーザーに委ねる前に本 skill を通す (完了後の検証だけでなく、着手前のゲートとしても使う。実行計画を明示的に検証させたところ、実行手順自体が導入バージョンで機能しない・測定が循環している等の致命的欠陥が複数見つかった、という実例がある。自己申告の自己反芻だけでは気づけなかった)
- **省略可**: 単発コマンド実行・ファイル検索・日常 Q&A など軽微な作業。成果物の採否が変わらないと明らかに判断できる場合
- **自作の重要な運用ルール (skill・検知ルール・設定ファイル・自動化スクリプト等) の更新も対象**: 自分が更新したこれらの成果物の完了報告前は本 skill を必ず通す。自己採点は複数のメカニズムで甘くなりやすい (作成者本人による評価バイアス・完了を急ぐインセンティブ等) ため、特にこの種の変更では独立検証を省略しない。変更検知の自動リマインド機構を設定している場合はそれに従う
- **これらのレベルの変更を対象とする設計・仕様書の承認依頼前も対象**: 上記の適用時点 (完了報告前) を、設計・仕様書の承認依頼前へ前倒しするもの。設計を提示し承認を求める時点が「完了報告」に相当する (Why: ある運用規範とその強制機構をセットで設計した際、本 skill を通さずに承認依頼を出したところ、適用後に致命的な欠陥が複数見つかり設計が大幅に修正された。承認判断を消費する前に潰すべきだった)

## 独立検証を default にする

自作の重要な運用ルール・自己評価では Phase 2 の独立 subagent (dispatch できるツールがあればそれ) を default で通す。ミニ検証 (下記) はそのようなツールが実測で利用不能と確認された場合の縮退経路であり、利用可能な状況で選ぶことは骨抜きになる。

- **default (独立 subagent)**: 汎用の独立 subagent を dispatch し、3〜5 レンズで指摘を求める。バイアスフリー条件 (§Phase 2) を厳守する
- **縮退 (ミニ検証)**: 独立 subagent の dispatch が利用不能な場合のみ。利用可否は事前に実測してから縮退を選ぶ

## ミニ検証 (縮退経路・独立 subagent 利用不能時のみ)

成果物を更新して完了報告する前の最低ラインとして、全 3 段クリアしないと「完了」「反映済み」「網羅した」等の完了系表現の断定は禁止する。

1. **真陽性テスト (実 FB 語彙)**: ユーザーが今回 NG と指摘した文字列・構文を検知ルールにぶつけ、**全件ヒット**するか機械実測する。判定質問型は 3〜4 パターンの活用形バリエーションを試す。1 件でも漏れたら合格しない
2. **偽陽性テスト (許容表現)**: 既存の許容表現など「検知されてはいけない表現」をぶつけ、誤検知ゼロを確認する
3. **外部ソース類似 NG テスト**: 実 FB に無い類似 NG 文で発火するか確認する。**類似 NG 文は自作しない (確証バイアス下の自作は独立性ゼロ)**。過去の FB ログ・別 skill の deny 例・ユーザーが指定した検証セット等、判断が入らない外部ソースから引く。外部ソースが得られない場合は「実 FB のみで確認済み・類似ケース未検証」と明示する

いずれかで漏れ・誤検知が出たら検知ルールを修正し、再度 3 段を通す。修正回数と結果を裁定表に残す。

### Phase 1: 検証設計

1. **対象成果物を確定する** — 何を検証するかを 1 文で定義する。曖昧なままだと指摘が散漫になる
   - **自作の重要な運用ルールの検証では、検証周の時点で既に存在する記録文書 (関連する意思決定記録・当該検証結論を記述した仕様書箇所) を成果物本体と同じ周で検証対象に含める**。まだ書かれていない記録文書 (反映後に書く PR 本文等) は対象にできないため、起草時点で本体の裁定と矛盾しないか別途照合する
2. **レンズを分割する** (2〜5 個) — 観点を混ぜると浅くなるため分割する。例: 「論理的整合性」「実行可能性」「セキュリティ」「ユーザー影響」「コスト」等。成果物の性質に合わせて設計する
   - **ネットワーク断・環境停止を伴う検証計画では「実行主体の依存関係」をレンズに含める**: 実行者自身がクラウド API 接続に依存して動作している点を踏まえ、① 各 Step の実行主体 (自動 / ユーザー) がその Step 時点の環境状態 (ネットワーク・設定・プロセス) で実行可能かを確認する ② 実行主体が担う Step の前提には「API 接続が生きていること」が置かれている、という事実を明示する (断・停止中は動作できない) ③ 環境状態を変える Step の直後に自動実行 Step を置かない (状態確認はユーザー報告や復旧後の観測で代替する) ④ **断・停止中に必要な操作はユーザー手動ステップとして設計する** (自動実行できないため代替不可)
3. **深刻度を定義する**:
   - **Critical**: 採用すると結論・方針が変わる致命的欠陥
   - **Major**: 修正すべきだが結論は変わらない
   - **Minor**: あれば良い改善
4. **反復上限を宣言する** — 既定 5 周。Critical が残っても上限到達で次フェーズへ進む

---

### Phase 2: 独立 dispatch

バイアスフリー条件を厳守する:

1. **subagent の独立性を確保する**:
   - 成果物の作成に関与していない subagent を使う
   - 複数のモデルを併用できる環境では、相異なる 2 モデル以上による多モデル panel 構成を許容する (単一モデルの自己相関バイアス回避)
2. **渡す情報を最小化する**:
   - 成果物本体 + 必要最小の背景のみ渡す
   - **作成経緯・自己評価・期待する結論は渡さない** (バイアス注入になる)
   - **ただし要件がユーザー由来である場合はその旨を明記し、「要件自体への疑義は技術的指摘と混ぜず別枠で出す」よう指示する** (期待する結論の注入ではなく、指摘の射程を分離させる指示。混ざったまま返ると親が射程を誤認し、要件否定を技術的 Critical と同列に扱ってしまう)
3. **レンズごとに指摘を出させる** — Phase 1 で定義したレンズを明示し、各レンズから独立した指摘を求める
4. **実 dispatch が技術的に不能な環境に限り** (独立 subagent の利用可否は事前に実測してから縮退を選ぶ) 役割演技 (自分でレンズ視点を演じる) で代替してよいが、真の独立性 (文脈遮断) を担保しない。この場合は裁定表に「role-play — bias-free な独立検証ではない」と明記し、消費者側が裁定の信頼度を割り引けるようにする

### 独立 subagent の直接呼び出しが使えない環境での実 dispatch

利用しているモデルの週次利用上限が逼迫している等の理由で、標準の subagent 呼び出し機構が制約される (例えば opus 級モデルへの委譲が enum 制約でブロックされる) 場合、代替として並列 fan-out 型の subagent 実行手段があればそれを使う。イメージは以下のような形になる:

```bash
lens_out=$(mktemp -t lens)
trap 'rm -f "$lens_out"' EXIT   # PII 混入対策: 集約 JSON は一時 file・完了後削除

{
  jq -cn --arg id lens-correctness --arg prompt "$P1" \
    '{id:$id, tier:"opus", prompt:$prompt}'
  jq -cn --arg id lens-security --arg prompt "$P2" \
    '{id:$id, tier:"sonnet", prompt:$prompt}'
} | your-subagent-runner --fanout --max-parallel 3 > "$lens_out"

# 各レンズの stdout を裁定に流す
jq -r '.results[] | select(.status=="ok") | "\(.id):\n\(.stdout)\n---"' "$lens_out"
# error レンズは summary.error>0 で警告表示
jq -r '.summary | if .error > 0 then "警告: \(.error)/\(.total) レンズ失敗" else empty end' "$lens_out"
```

**制約**:
- schema-forced structured output は無い (prompt で「必ずこの JSON で返す・fence 禁止」と指示 + fence 除去の後処理が要る)
- context 継承なし (prompt に必要な文脈を詰める)
- fanout の仕組みは個別失敗を silent に混ぜて exit=0 で返すことがある → 呼び出し側で失敗件数を明示的にチェックする

### Phase 3: 裁定

0. **指摘の射程を分類する (裁定の前に必ず行う)** — 深刻度 (Critical/Major/Minor) とは独立の軸。射程を誤ると、ユーザーが定めた要件が subagent の提案に上書きされる:

   | 射程 | 内容 | 裁定権限 |
   |---|---|---|
   | **実装 (How)** | 前提を認めた上で実現方法の欠陥を突く | 実データで裏取りして裁定する |
   | **要件 (What)** | ユーザーが定めた要件・制約自体を否定する | **裁定しない。ユーザーに諮る** |
   | **目的 (Why)** | そもそもやる必要がないと主張する | **裁定しない。ユーザーに諮る** |

   - **要件・目的の射程は、Critical であっても独断で採否を決めない**。「reviewer がこう言っている」とユーザーに提示して判断を仰ぐ (ユーザーの元依頼を reviewer 提案で上書きするのも同じ禁止に当たる)
   - **射程の広げすぎに注意する**: 実装射程の指摘 (例: 「ファイル受け渡しが破綻する」) を根拠に、要件射程の結論 (例: 「この手段自体をやめる」) へ拡張しない。指摘が潰しているのは実現方法の一部であって、要件ではない
   - reviewer は前提そのものの要否を疑うのが役目なので、dispatch で「要件は前提」と書いても越境してくる。越境自体は正常で、**扱いを誤らないことが親の責務**
   - (Why: ある設計で「注入 UI 自体が過剰」という要件否定を Critical として無批判に採用し、ユーザーの元の要件 (レンダリング表示を見ながら書きたい・ツール切り替えがコスト) を捨てた実例がある。技術的指摘 (ある実現方式が破綻する) は本物だったが、それは「その実現方式をやめる」理由であって「機能自体をやめる」理由ではなかった。ユーザーに一言聞けば分かることを聞かずに reviewer を採った)

1. **指摘を実データで裏取りする** — 「一般論は正しいが当該ケースに当たらない」ことがある。全体を渡せていないレビューの指摘に盲従しない
2. **裁定区分を決める**:
   - **採用**: 指摘が正当で成果物への反映が必要
   - **部分採用**: 方向性は正しいが範囲・方法を調整
   - **却下**: 当該ケースに当たらない・前提が異なる (却下理由を明記)
3. **裁定表を作る**:

   | 指摘 | レンズ | 深刻度 | 裁定 | 根拠 |
   |---|---|---|---|---|
   | (指摘内容) | (観点) | Critical/Major/Minor | 採用/部分採用/却下 | (実データに基づく理由) |

---

### Phase 4: 反映

採用・部分採用の指摘を成果物へ反映する前に、以下を確認し結果を裁定表に一言残す (自己問答で終わらせない):

- **指摘が示した問題の広がりを 1 文で言語化する** — 「A 単体の欠陥」なのか「A と B の関係の欠陥」なのかを区別する (Phase 3 手順 0 の射程分類とは別の軸)
- **提示された修正案があっても逐語採用しない** — 広がりに対して過不足がないかを検査し、検査した対象と結果を裁定表に書く
- **反転で対処しない** — 「向きが逆」「一方に寄っている」型の指摘を単純に逆向きにすると過剰修正になる。両立させる設計を先に検討する
- **修正後、その修正が他の条件・記述と矛盾しないかを反映と同じ周で確認する** — 照合した箇所を裁定表に書く (次周まで持ち越すと発見が遅れる)。ここでの矛盾チェックは自分の修正起因のものに限る。独立検証での再検出は Phase 5 が担う (役割は重複しない)

反映後に変更内容を裁定表に追記する。

**成果物の編集権限がない場合** (第三者レビュー・机上シミュレーション等): Phase 4 を「反映方針の提示」に読み替える。実際の改訂は行わず、採用・部分採用の指摘それぞれについて「どう直すか」を裁定表に明記するに留める。

---

### Phase 5: 反復判定

**「1 周目の Critical を全件反映した」を新規ゼロの根拠にしない。** 反映した版に対してもう 1 周かけ、そこで新規 Critical が出ないことを確認して初めて完了とする。修正は欠陥を消す行為であると同時に**新しい前提を持ち込む行為**なので、個別には正しい修正の組み合わせが破綻することがある。

2 周目以降は範囲を絞ってコストを抑える。全レンズを再走させず、次の 3 点に限定する:

1. 改訂で新たに混入した矛盾 (直した箇所と他の節の整合)
2. ゲート・判定条件が判定装置として機能するか (合格条件の有無)
3. 裁定表と本文の一致 (「採用・反映先 §X」がその節に本当に反映されているか)

3 周目以降は Critical の有無だけを問う (Major/Minor の列挙を求めない)。

- **Critical 指摘が新規ゼロ** → 完了。裁定表を成果物本体または検証レポートに記録する
- **Critical 残存かつ上限未達** → Phase 2〜4 を繰り返す (周回数を記録する)
- **上限到達で Critical 残存** → 「条件付き Go」として残余リスクと対応方針を成果物に明記して終了
- **編集権限がなく実改訂サイクルを回せない場合**: 「提示した反映方針が適用されたと仮定して新規 Critical が出るか」を裁定者が机上で判定し、これを 1 周として数える。この机上判定周を「上限到達」と混同せず、**Critical が採用された周を「完了」や「新規 Critical ゼロ」と誤判定しない** (Critical が残る限り、実確認が取れるまでは「条件付き Go」として扱ってよい。上限未達なら机上判定周を重ねる、または実確認手段自体がないことを明記して打ち切る)

---

### Phase 6: 較正 (検証者の検証)

検証の精度は「強いモデルだから大丈夫」でなく実測で管理する。

1. **seeded defect 検査**: 既知の欠陥を意図的に混入した成果物を定期的に (または重要案件の検証前に) 検証させ、見逃したらレンズ設計・dispatch プロンプトを修正してから本番検証に進む
2. **すり抜け欠陥の事後分析**: 検証を通過した成果物から後日バグ・考慮漏れが発覚するたびに、根本原因分析の手順で「どのゲート・レンズが捕まえるべきだったか」を分析し、Phase 1 のレンズ設計・深刻度定義に反映する

## 注意事項

- **裁定は自分 (検証を主導する側) が行う** — subagent の指摘を全採用しない。「指摘された = 修正必要」ではない。実データ裏取りが必須
- **裁定の前に射程を分類する** — Phase 3 手順 0。要件・目的の射程 (ユーザーが定めた要件そのものの否定) は Critical でも独断で採否を決めず、ユーザーに諮る。実装射程の指摘を根拠に要件射程の結論へ拡張しない
- **自動却下もしない** — subagent が計画・仕様の意図と矛盾する finding を出しても独断で却下しない。計画で定められた方針と reviewer の代替提案が対立するときはユーザーの判断を仰ぐ (reviewer の代替設計が優れる可能性を既定値で候補から外さない)
- **実データで再現した plan-mandated な real bug はまとめて修正する** — reviewer が実データで再現した (一般論への盲従でなく裏取り済みの) real bug は、都度確認を取らずに fix 設計を確定し、修正を進めてよい。完了報告・PR 本文でまとめて列挙し、ユーザーが確認できるようにする (**merge は依然ユーザー許可** — 都度確認を省く分の補償統制として維持する)。ただし **設計変更 (仕様改定・不可逆操作の方針転換・整合性検証手段の導入等) を要するもの**は従来どおり諮る
- **反復は Critical に絞る** — Major/Minor は初周で対処し、2 周目以降は Critical のみを追う (コスト管理)。**初周で Major/Minor と裁定済みのものは 2 周目以降蒸し返さない**。2 周目以降に新規発生した指摘は Phase 3 の深刻度裁定 (既存フローの一部・追加コストではない) を通し、そこで「Critical 相当の兆候が読み取れない」と 1 文で判断できればそのまま切り捨ててよい (全件の再吟味を求めるものではない)
- **バイアス注入厳禁** — dispatch 時に「問題はないと思うが確認してほしい」等の誘導を入れない
- **省略は明示する** — 軽微な作業で省略した場合は「adversarial-review-loop 省略 (理由: 単発コマンド実行)」と一言記録する
