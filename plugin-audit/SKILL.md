# Skill: Plugin Audit

Claude Code の挙動に影響する外部ファイル (plugin / skill / hooks) の導入時に自動でセキュリティ・品質チェックを行い、危険な導入をブロックする。

## 起動条件

- ユーザーが `/audit-plugin` を明示的に実行した
- PostToolUse hook を設定している場合、対象ファイルの変更を検知して警告を出す運用にもできる (hook はスキル本体を自動実行しない前提とする。hook の実装自体は本 skill のスコープ外)。手動起動 (`/audit-plugin`) が確実な経路

以下のファイルが変更された場合に監査を推奨する:

- `settings.json` の `enabledPlugins` に新規エントリが追加された
- `.claude/skills/` 配下に新規 `.md` ファイルが追加された
- `.claude/hooks/` 配下にファイルが追加・変更された
- `hookify.*.md` ファイルが追加・変更された

---

## Phase 1: 対象の特定

### 検出対象

| 種別 | パス / 設定 | 検出方法 |
|------|------------|---------|
| Plugin | `settings.json` → `enabledPlugins` | 差分検知 or ユーザー指定 |
| Skill | `.claude/skills/**/*.md` | 新規・変更ファイル |
| Hooks | `.claude/hooks/**` / `hookify.*.md` | 新規・変更ファイル |

### 対象ファイルの収集

1. `git diff --name-only` で変更ファイルを検出
2. Plugin の場合は GitHub リポジトリ URL からソースを取得 (WebFetch)
3. 全対象ファイルの内容を Read で取得

---

## Phase 2: セキュリティチェック

各対象ファイルに対して以下の観点でチェックする。

### チェック項目

| # | 観点 | チェック内容 | Fail 条件 |
|---|------|------------|----------|
| S1 | シェル実行 | `bash`, `sh`, `exec`, `system`, `subprocess`, `child_process` の存在 | 未説明のシェルコマンド実行が含まれる |
| S2 | Hooks 注入 | `PreToolUse`, `PostToolUse`, `hooks` の定義・変更 | ユーザー承認なしに Hooks を追加・変更する |
| S3 | permissions 変更 | `permissions.allow`, `permissions.deny` の操作 | deny ルールの削除・allow への昇格 |
| S4 | 秘匿情報アクセス | `.env`, credentials, token, secret, key パターン | 秘匿ファイルの読み取り・送信 |
| S5 | 外部通信 | `curl`, `wget`, `fetch`, `http`, 外部 URL | 未説明の外部エンドポイントへの通信 |
| S6 | ファイル削除 | `rm`, `unlink`, `delete`, `rmdir` | 広範なファイル削除操作 |
| S7 | 権限昇格 | `sudo`, `chmod 777`, `--no-verify`, `--force` | 安全装置の無効化 |

### 判定基準

| 判定 | 条件 |
|------|------|
| **Pass** | 全チェック項目で問題なし |
| **Warn** | S5 (外部通信) が検知されたが説明可能 / S1 が限定的なコマンドのみ |
| **Fail** | S2〜S4, S6〜S7 のいずれかに該当 / S1 で未説明の任意コマンド実行 |

### 外部スキャナの定型警告 (triage 方針)

外部の脆弱性スキャナが具体的な脆弱性内容を示さず「High Risk」等の定型的な警告のみを返すことがある。これは Phase 2 の S1〜S7 (本 skill の自前静的解析) のいずれにも該当しない別軸の入力であり、他のシグナル (別スキャナが clean・作者の素性が確認済み・SECURITY.md 等の対策明記) が健全なら、導入をブロックせず継続監視の対象として認識するに留めてよい。

判断手順: ① 他スキャナの結果・作者の実在性・公式のセキュリティ文書の有無を確認する ② それらが概ね健全なら導入をブロックしない ③ 継続監視の対象として認識だけしておく (能動的な定期スキャンの自動化までは要求されない。求められたら定期実行の仕組み化を検討する)。

継続監視の状況は skill 本体とは別の場所 (メモ・チケット等) で個別管理してよい。

## Phase 3: 品質チェック

| # | 観点 | チェック内容 | Warn 条件 |
|---|------|------------|----------|
| Q1 | 提供元 | Anthropic 公式か否か | 非公式 (コミュニティ製) |
| Q2 | ソース可読性 | ソースコードが公開・監査可能か | クローズドソース or 難読化 |
| Q3 | 活動状況 | 最終更新日、Star 数、コミット数 | 6 ヶ月以上未更新 / Star < 10 |
| Q4 | ドキュメント | README / 利用説明の有無 | ドキュメントなし |
| Q5 | 依存関係 | 外部依存の数と安全性 | 未検証の依存が 3 つ以上 |

## Phase 5: Fail 時の挙動

### ブロック処理

1. **導入を中止する**: ファイルの追加・設定変更を実行しない
2. **理由を提示する**: どのチェック項目で Fail したか具体的に表示
3. **override オプション**: ユーザーが明示的に「リスクを承知で導入する」と宣言した場合のみ続行を許可

### override フロー

```
⚠ FAIL: [対象名] — S2 (Hooks 注入が検知されました)
   検知内容: PreToolUse hook が追加され、Bash コマンドを検査します
   
   導入を中止しました。
   override する場合は「リスクを承知で導入する」と明示してください。
```

ユーザーが override を宣言した場合:
- Warn に降格して導入を続行
- 監査ログとして結果をメモ (feedback type) に保存

## Phase 6: ADR 記録

以下のいずれかに該当する場合、ADR (Architecture Decision Record) を作成する:

| 条件 | 理由 |
|------|------|
| plugin 導入が既存の防御層と重複・再編を伴う | 「何を残し何を外したか」が後で追えない |
| permissions.deny / hooks の大幅な追加・削除がある | セキュリティポリシーの変更は意思決定として記録すべき |
| Fail → override で導入を強行した | リスク受容の記録 |

### ADR の出力先

- プロジェクトの ADR (Architecture Decision Record) 置き場に出力する。無ければユーザーに保存先を確認する
- フォーマットは Context / Decision / Consequences 等、一般的な ADR 形式に準拠する

### 記載必須項目

1. **検討した代替案** (少なくとも 2 案)
2. **重複・整理した防御層** (何を無効化/維持したか)
3. **Rollback 手順**

---

## Phase 7: Upstream フィードバック

plugin 導入後、以下の観点で upstream リポジトリへの issue/PR を検討する:

| 観点 | アクション |
|------|-----------|
| plugin がカバーしていない脅威パターンを利用者側で補っている | issue: 検知パターン追加の提案 |
| テンプレートに不足・誤りがある | issue or PR: テンプレート修正 |
| ドキュメントが不明瞭 | PR: README / SKILL.md の改善 |
| バグや誤検知を発見した | issue: 再現手順付きで報告 |

### 実行フロー

1. 導入作業中に気づいたギャップをリストアップ
2. ユーザーに「upstream に issue/PR を上げるか」を確認
3. 承認されたら gh CLI でアカウントを確認のうえ作成

---

## Phase 8: 監査ログ

全チェック結果を以下に記録する:

- **Pass / Warn**: 会話内での報告のみ (ログ不要)
- **Fail → override**: メモに保存 (いつ・誰が・何のリスクを承知で導入したか)

## 新規プラグインの命名規則 (公式優先)

社内 marketplace 等、独自のプラグイン配布の仕組みを持つ場合、新規プラグインを追加するときの命名は、**独自の既存慣習よりも Anthropic 公式の命名規則を優先する**。

| 対象 | 公式規則 (出典: code.claude.com/docs) |
|---|---|
| plugin `name` | kebab-case・スペース禁止。**`-plugin` サフィックスは公式慣習に無い** (公式例: `code-review` / `frontend-design`) |
| skill `name` | 省略可 (ディレクトリ名=コマンド名)・kebab-case |
| agent `name` | 必須・kebab-case。**プラグイン内 agent は自動で `plugin名:agent名` に namespace される** → 自前でプラグイン名プレフィックスを付けるのは冗長 |

- **Why:** 既存プラグインが独自の命名慣習で一貫していても、将来の互換性・他者の理解しやすさを優先するなら公式準拠に寄せる方が有利
- **トレードオフ:** 既存の慣習付き命名とは浮くことがある。既存の一括リネームは blast radius が大きく別タスクとして扱う
- 命名・API・仕様など**公式に正解がある領域は、局所基準だけで断定せず公式 docs を先に引く**。公式と独自慣習が食い違う場合は両方を提示しトレードオフを示して選ばせる

## 注意事項

- 公式プラグインであっても Hooks 注入を伴うものは Warn を出す
- チェックは静的解析のみ。実行時の動的挙動は対象外
- Plugin のソースが取得できない場合は Q2 で Fail
- 複数ファイルが同時に追加された場合は各ファイルを個別にチェック
