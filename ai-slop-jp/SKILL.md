# AI 臭を抜く日本語ライティング規範 (コア)

対象は日本語ライティング全般 — SNS 投稿・チャット・報告書・運用文書・技術記事。狙いは「誰が書いてもよかった文章」を「この書き手・この場面にしか成立しない文章」に変えること。

AI 臭は表現の癖ではなく**生成過程の癖**から生じる。だから症状 (§4) を潰すだけでは足りず、原因 (§1) を知り、人間らしさの要素 (§2) を文書種に合う形 (§3) で入れる。手順は §0 に固定してある — 手順どおりに回せば、実行するモデルによらず同じ結論に着地するように設計している。手順を飛ばして「感覚で」直さない。

## 0. 固定手順 (この順で必ず回す)

0. **対人成果物なら読み手の軸値を先に確定する** — 他者に読ませる文書 (レビュー・報告書・周知文・提案資料・運用文書・仕様書・記事) は、書き始める前に読み手の属性 (立場・関係性・前提知識・目的) から、用語レベル・詳しさ・形式・トーン・依頼の置き方の 5 軸を引いて宣言する (専用の読み手プロファイリング手順を別途用意しているなら、それに従ってよい)。**本手順 (§0) は「書いた文の AI 臭を抜く」ための手順で、読み手の軸決めは「誰に向けて書くか」を決める前工程**。H5 (特定の読み手) の具体化はこの前工程が担うため、本 skill では重複実装しない。既存文の推敲のみで書き手が自分でない場合はスキップしてよい。
1. **文書種を判定する** (§3 の表)。迷う・混在するときはユーザーに確認する (過去、運用周知に主張文の軸を機械適用して却下された)。**表・コードブロックのみで地の文がほぼ無い技術参照文書 (実装ガイド・脅威対策レポート等) は診断対象外と判定してよい** — AI 臭が宿る narrative prose の面積が無いため。frontmatter (`source:`/`confidentiality:` 等) + `[[wikilink]]` が高密度な文書は、読み手が「対人」か「自己参照 (ナレッジベース)」かを先に見極める (後者は太字・省略の基準が異なる可能性があるため判定を保留してよい)。
2. **該当 case module を Read する** (`modules/case-*.md`)。較正済み before/after 実例と文書種固有の deny 表がある。書き手が本人名義の文書で、**かつ §3 マトリクスで H6 (声) が ✗ でない文書種**なら、(用意していれば) 自分の声のプロファイル module も Read する (運用文書では読まない — 声を出さない文書種のため)。SNS の**ペルソナアカウント運用**は、そのアカウント専用のプロファイル・NG 定義があればそちらを正とし、本人の声プロファイルは使わない。
3. **ゼロベースで書く**。リライトでも元文の語彙・構文・段落構成をなぞらない (§6 鉄則 2)。
4. **機械ゲートを通す**。§4 の deny 表 (+ case module の追加分) に文字列レベルで照合し、ヒットを全て処置してから先へ進む。ここに判断は要らない。scope 注記付きの項目 (#10「SNS/チャット」等) は該当文書種でのみ照合する。**照合対象は本文だけでなく見出し・タブ名・セクション名・項目名も含める** (特に #21 は見出し・ラベルが主対象。本文だけ削って見出しを疑問文・説明句のまま残す適用漏れを防ぐ)。`/slop` 明示起動時、および判定に迷う症状が出たときは `modules/smell-catalog.md` (全カタログ・SSOT) まで Read する。
5. **採点する**。§5 のアンカーに照らし、文書種の適用軸のみ各 1-10。**適用軸の平均 7.0 未満 (5 軸フル適用なら合計 35/50 未満) は書き直し**。最低点の軸から直し、再採点する (最大 3 周。届かなければ最終採点と残課題を添えて提示する)。
6. **採点と処置した症状を添えて提示する**。

**自分の生成文にも同じ手順を通す (最重要の運用)**。`/slop` が起動されていなくても、投稿文・見出し・キャッチコピー・候補案を生成してユーザーに出す瞬間が適用タイミング。複数候補は各候補を採点する。過去、生成と精査を別物として運用し、AI 臭い候補をそのまま提示して却下された。

## 1. AI 臭の 8 原因 — なぜ AI の日本語は AI 臭いか

症状の根はこの 8 つ。処置に迷ったら「どの原因から出た症状か」に戻ると判断が安定する。

| # | 原因 | 生成過程で起きること | 代表症状 (→ §4 / catalog) |
|---|---|---|---|
| C1 | 最頻値への回帰 | 分布の中心 = 誰もが書きそうな表現を選ぶ | 輪郭のない一般語・紋切り型・バズワード |
| C2 | 全方位への配慮 | 誰からも反論されない文に寄せる | 両論併記・留保逃げ・立場の不在 |
| C3 | 均質な情報密度 | 全文が同じ濃さ・同じ文長で進む | 文末単調・文長均一・接続詞連打 |
| C4 | 読者の不特定 | 特定の誰かに向けて書かない | 誰にも刺さらない全方位文・丸投げ疑問 |
| C5 | 体験の不在 | 一次体験を持たないため抽象論か「それっぽい例」に流れる | テンプレ感想・捏造風の例え話・成果の抽象化 |
| C6 | 「ちゃんと書いてる感」の演出 | 中身の薄さを構造マーカーで補償する | 対句の決め台詞・締めの悟り・絵文字盛り・箇条書き逃げ・飾り記号・予告と総括 |
| C7 | 書き言葉バイアス | 学習の中心が文書のため、話す場でも文書語が出る | チャット/SNS へのビジネス名詞・過剰敬語の混入 |
| C8 | 完結強迫 | 省略・言い差し・余白を許容できない | 全部説明する・必ずまとめて閉じる・網羅返信 |

## 2. 人間らしさの 8 要素

AI 臭の除去 (引き算) だけでは「無臭で無個性」までしか行けない。人間の文章にするには足し算がいる。ただし**どの要素が効くかは文書種で変わる** (§3)。

| # | 要素 | 中身 |
|---|---|---|
| H1 | 立場 | 賛否・好き嫌いを切る。逃げ道を残さない |
| H2 | 一次体験 | 見た・やった・失敗した具体。数字と場面 (捏造禁止 → §6 鉄則 1) |
| H3 | 温度 | 驚き・苛立ち・興奮の手触り。無菌の説明調に均さない |
| H4 | ムラ | 思い入れの偏り。厚く書く所と一行で流す所の差 |
| H5 | 特定の読み手 | 顔の見える誰か一人に向ける (属性から調整値を引く規則は読み手プロファイリングの前工程が SSOT) |
| H6 | 声の癖 | 語彙・文末・記号の一貫した個性 (本人名義なら自分の声のプロファイルを事前に定義しておくと精度が上がる) |
| H7 | 省略と余白 | 全部言わない。読み手が補える所は任せる |
| H8 | 時間性 | 「昨日」「さっき」の生っぽさ。総括済みの過去形に均さない |

## 3. 文書種の判定と適用マトリクス

| 種 | 例 | module |
|---|---|---|
| (a) SNS 主張文 | Threads/X/FB 投稿・告知・キャッチコピー | case-sns |
| (b) チャット | Slack/Teams のメッセージ・依頼・会話・軽い連絡 | case-chat |
| (c) 報告書 | 業務報告・評価入力・稟議・議事要旨 | case-report |
| (d) 運用文書 | 運用ルール・マニュアル・手順書・正式な周知 | case-ops-doc |
| (e) 技術記事 | 記事・解説・ブログ (論証は長文向けの専用文章規範を併用) | case-article |
| (f) 仕様書・要件定義書・設計書 | 要件定義書・設計書・仕様書 (エンジニア / 非エンジニア意思決定者向け) | case-spec-doc |
| (g) Claude 応答 | 完了報告・調査報告・受領・recap・insight | case-claude-reply |
| (h) レビューコメント | PR/issue のレビュー指摘・返信 | case-review |
| (i) 発声台本 | 登壇・プレゼン・研修のトークスクリプト (声に出して読む) | case-talk-script |

(b)/(d) の境界: **期日・必須アクションを伴う正式な周知は、配信先が Slack でも (d)**。雑談的な軽い連絡・依頼・会話は (b)。Slack 投稿の導入行 (名乗り) だけ (b) で書き、本文を (d) で書く分離も可。

| H2 一次体験 | ◎ | △ | ◎ (事実として) | ✗ | ◎ (導入・失敗談) | ✗ | ✗ | ✗ | △ |
| H3 温度 | ◎ | ○ | △ | ✗ | △ | ✗ | ✗ | ✗ | △ |
| H4 ムラ | ◎ | ○ | ✗ | ✗ | ○ | ✗ | ✗ | ✗ | ○ |
| H5 特定の読み手 | ◎ | ◎ | ○ (宛先) | ◎ (作業者) | ◎ (想定読者) | ◎ (読者レベル) | △ | ◎ | ◎ (聴衆) |
| H6 声の癖 | ◎ | ◎ | △ | ✗ | ○ | ✗ | ✗ | △ | ○ |
| H7 省略と余白 | ◎ | ◎ | △ | ✗ | △ | ✗ | ○ | ○ | ○ |
| H8 時間性 | ◎ | ◎ | ✗ | ✗ | △ | ✗ | ✗ | ✗ | △ |

✗ の欄に要素を足すのは誤適用 (運用周知に煽りフックや書き手の心情を足す等)。(d) で人間らしさが現れる場所は文体ではなく**読み手への想像力** — 作業者の文脈に沿った順序、つまずきの先回り、迷わせない具体。

## 4. 機械ゲート (最頻 20・判断不要)

文字列レベルで照合し、ヒットは削除か置換。**照合はリテラル (表の文字列・条件) のみ** — 表に無い近縁語 (「大幅に」等) をヒット扱いにせず、§5 の採点側で拾う。全量 SSOT は `modules/smell-catalog.md` (原因への紐付け・境界条件・誤検知の扱いはそちら)。

| # | 症状 | 検知 | 処置 |
|---|---|---|---|
| 1 | テンプレ感想 | 「刺激的でした」「学びの多い時間」「〜に感謝です」 | 具体の事実 + 温度に置換 |
| 2 | 締めの悟り構文 | 末尾の「大事なのは〜」「〜していきたいと思います」「〜かもしれません。」 | 削除するか、立場の言い切りに置換 |
| 3 | 対句の決め台詞 | 「〜ではなく、〜」「X は〜。でも本当は〜」が 1 文書に 2 回以上 | 1 回まで。残りは平叙文に |
| 4 | 丸投げ疑問 | 「〜ではないでしょうか」「あなたはどうですか?」「いかがでしたか」 | 断定に直すか削除 |
| 5 | 両論併記逃げ | 「良い面も課題もある」「一長一短」(結論なし) | 立場を選んで言い切る |
| 6 | 留保逃げ | 「〜とは限りません」「〜という側面もあります」 | 根拠があれば断定へ。反例が実在する主張のみ留保可 |
| 7 | 輪郭のない一般語 | 効率化・最適化・活用・向上・課題・推進・実現・強化 | その場の具体 (数字・行為) に置換 |
| 8 | 空虚な強調 | 非常に・極めて・圧倒的に・革命的・劇的に | 数と事実で語る |
| 9 | バズワード | シナジー・パラダイムシフト・ゲームチェンジャー | 自分の言葉に言い換え。できなければ削除 |
| 10 | ビジネス名詞の混入 (SNS/チャット) | 接触・実施・取り組む・活用する | 口語動詞に (使う・やる・送る・動く) |
| 11 | 過剰敬語・クッション連打 | 「お忙しいところ恐れ入りますが」等が 2 回以上・「させていただく」多用 | クッションは 1 回まで。用件を先に |
| 12 | 行頭絵文字列 | ✅🔥✨💡 等の行頭連続 | ゼロにするか、効く 1 個 |
| 13 | 「!」連発 | 1 文書に 3 回以上 | 1 回まで (voice profile が許す場合を除く) |
| 14 | 箇条書き逃げ | 地の文 2〜3 文で言える内容の ①②③ 分解 | 地の文に戻す |
| 15 | 飾り記号 | 【重要】・★・◆・意味のない「——」 | 削除。中身で引く |
| 16 | 文末単調 | です/ます が 3 文以上連続 | 体言止め・言い切り・短文をぶつける |
| 17 | 接続詞連打 | また・さらに・そして・加えて の規則的連続 | 削るか論理を組み直す |
| 18 | 予告と総括 | 「今日は〜について」「まとめると」(短文で) | 本題から入る。まとめずに終わる |
| 19 | 口語副詞の後付け | 非口語文への「ぶっちゃけ」「めちゃ」「正直」添加 | 削除 (乗せても口語にならない) |
| 20 | 捏造風の例え話 | 「例えばあなたが〜だとしましょう」 | 実例に置換するか削除 (→ §6 鉄則 1) |
| 21 | 見出し・ラベルへの説明句詰め込み | タブ名・セクション見出し・項目名に括弧補足・「〜を〜する」説明句・フレームワーク略語 (BMC/VPC/7Powers/MVP/SLA 等)・社内独自の採点コードや分類記号 (s1/s2・w1・A/B/C 等) を含む | 端的な体言止め (目安 8〜10 字) に削ぎ落とし、説明は本文・リードへ。非エンジニア向け資料ではフレームワーク略語も社内コードも、読み手が知らない前提で「状態を表す平易語」に置換する (例: s1→手作業中心 / A→全体像のインプット不足) |
| 22 | タグライン見出しの反復 | 見出し・章題・項目名に「A が、B。」「A を、B する。」型 (助詞直後の読点 + 言い切り。動詞終止・体言止めのどちらも) が同一文書で通算 2 件以上 | 体言止めの短句に圧縮 (「課題は、意思決定の遅れ。」→「意思決定の遅延と改善策」)。1 箇所のみの使用 (キービジュアル・扉) は対象外 |

## 5. アンカー付き採点

適用軸 (§3 の表の最終行) のみ採点する。アンカーは実文で較正してある — **低の実文に近ければ 1-3、高の実文に近ければ 8-10** で機械的に付け、中間 (4-7) は「どちらに近いか」で寄せる。

| 軸 | 問い | 低 (1-3) の実文 | 高 (8-10) の実文 |
|---|---|---|---|
| 立場 | 主張が 1 秒でわかるか | 「生成 AI には良い面も課題もある」 | 「『フルリモート=自由』はウソ。」 |
| リズム | 音読して単調でないか | 「〜です。〜です。〜です。」(同じ文長が並ぶ) | 「〜した事例。」(体言止め) →「〜していきたいものですな。」(崩し) の緩急 |
| 主体性 | この人しか書けないか | 「プロンプトは具体的に書くと精度が上がります」 | 「『いい感じにして』で 3 回やり直した」 |
| 具体性 | 具体・数・事実で語っているか | 「業務効率が大幅に向上しました」 | 「毎朝 30 分かけてた集計が、3 分で終わるようになった」 |
| 削減 | 削れる語・飾りが残っていないか | 行頭絵文字 + 「!」連発 + 「非常に」 | 効く一語だけ残して削ぎ落とされている |

- 採点は「初見の読み手」のつもりで付け、迷ったら低い方に倒す (甘い採点は書き直しの機会を奪う)。
- 短い文章ほど一軸の低さが全体を殺す。合計より先に最低点の軸を潰す。
- **入力事実 (書き手から引き出せた素材) に無い要素は補わず、その欠けを減点しない** (鉄則 1 が優先)。ただし事実の論理的帰結 (「未精算分が無ければ対応不要」等) は補ってよい。

## 6. 鉄則 (文書種によらず常時適用)

1. **体験・事実を捏造しない**。元ドラフトに一次体験がなければ「それっぽい失敗談」を創作せず、書き手に「使える体験・数字はあるか」を問う。引き出せなければ、その箇所は具体に踏み込まず立場と温度だけで立てる。
2. **リライトはゼロベース**。元文の語彙・構文・段落構成をなぞる「寄せた整形」は AI 臭を温存する。元文を一度脇に置き、文脈・主張・書き手の声から組み直す。確定済みの箇所は変えてよいか必ず確認する。**確定済みには「ユーザーが『この通り』と指定した箇所」だけでなく「既に投稿・提出済み / ユーザーが受諾済みの成果物」も含む** — これらへの一括書き換え提案を出す前に、編集履歴を増やす価値があるかを問う。ゼロベースは捏造の許可ではない (→ 鉄則 1)。
3. **確認への回答を本文に流し込まない**。書き手に事実確認したときの回答の言い回し (「A ではなく B」の対比枠) は書き手の頭の整理であって、読者に出す情報ではない。素材として咀嚼し、読み手に見せる文として書き直す。
4. **連作は隣に揃える**。Q&A の一問・連続スレッド・文書群の一部を書くときは、隣の項目の分量・段落数・文体・敬体常体を実測して合わせる。基準は自分の美意識ではなく隣の項目。**適用境界 (provisional・n=1)**: この鉄則が効くのは隣と並べて読む/比べる文書 (Q&A 回答集・連続スレッド・文書群)。各項目が独立に機能し正誤判定されるもの (クイズ選択肢・独立チェックリスト項目) には適用外 — 「揃えることに読み手価値があるか」で適用可否を判定する (機械適用しない)。
5. **固有表現を乱発しない**。書き手の癖を乱発すると新種の AI 臭 (物真似臭) になる。(声のプロファイルで頻度上限を決めているなら、それに従う。)

## 起動条件

- 手動起動 (自動発火機構は持たない)。日本語の文章を書く/推敲するとき、短文・見出し・投稿文をユーザーに提示する直前の自己精査として、または `/slop` で起動する。
- v1.x (短文・主張文特化) からの変更: 適用範囲を全文書種に拡大し、軸の適用が文書種で変わる (§3)。5 軸・閾値 (平均 7.0 = 35/50)・鉄則は継承。

## 注意事項

- **modules の Read は手順 (§0) が指定したものだけ**。全 module の一括 Read はしない。
- modules 構成 (10 本): `modules/smell-catalog.md` / `modules/case-sns.md` / `modules/case-chat.md` / `modules/case-ops-doc.md` / `modules/case-report.md` / `modules/case-article.md` / `modules/case-spec-doc.md` / `modules/case-claude-reply.md` / `modules/case-review.md` / `modules/case-talk-script.md`
- **棲み分け**: 長文論証の段落構成・論理の厳密さ・見出しは専用の長文文章規範が担当し、本スキルは AI 臭と声を担当する。技術記事は両方を使う。共通 AI 臭カタログの SSOT は `modules/smell-catalog.md` で、長文文章規範側にある対応表は長文特有型に絞ったサブセットになる想定。
- **視覚デザインとの棲み分け**: HTML/UI 等の視覚成果物の見た目 (AI default 検収・taste) は `../frontend-taste/SKILL.md` が担当し、本スキルはその成果物中のコピー (文言) を担当する。frontend-taste 側の視覚 Pre-Flight は文言項目を持たない (相互参照)。
- **SNS 運用との関係**: 見つけたネタを投稿文に仕上げる最終工程として使う。ペルソナアカウントの口調・NG はそのアカウント専用の定義があればそちらを正とし、本人の声プロファイルは使わない (§0 手順 2)。
- **社内文書のトーンとの関係**: 社内文書は組織のトーン規定 (過剰なへりくだりを避けた対等な礼節など) を基調にし、本スキルはその範囲で品質を上げる。
