# Case: 技術記事 (記事・解説・ブログ)

## 目的関数

読み手が論理を追えて、かつ「この人が書いた」とわかる。論証の厳密さと書き手の声を両立させる。

## 適用 (役割分担が前提)

- **論証・段落構成・認知負荷・見出しは専用の長文文章規範が SSOT**。本 module は技術記事に特有の AI 臭と、声を入れてよい場所だけを定める
- 効く要素: H2 一次体験 ◎ (導入・失敗談) / H1 立場 ○ (考察・結論) / H5 想定読者 ◎。本文の論証パートでは H3 温度・H4 ムラを抑える (長文文章規範の「演出の抑制」の考え方に従う)
- 採点軸: 5 軸フル (導入・考察は特に立場・主体性を重く見る)。合計 35/50 未満は書き直し
- 本人 register: (用意していれば) 自分の声のプロファイルの register 定義に従う (一人称は媒体で使い分ける想定。サンプルが薄い場合は初回執筆時に本人へ確認し、プロファイルに追記していく)

## 声を入れる場所 / 入れない場所

| 場所 | 声 | 理由 |
|---|---|---|
| 導入 | ◎ | 「なぜ自分が書くか」= 一次体験と立場が読む理由を作る |
| 手順・論証の本文 | ✗ | 正確さが主役。長文向けの文章規範で書く |
| 詰まった話・失敗談 | ◎ | この記事にしかない価値。具体の数字と現象で |
| 考察・結論 | ○ | 立場を切る。ただし悟り構文でなく根拠つきで |

**一次体験が無い記事の扱い**: 導入前の社内解説メモ (実装前で実測・失敗談が無い) は H2 一次体験を △ とし、無くても減点しない。固有価値は「体験」でなく「自社=当該業界での判断」で出す (下記「公式 doc の言い換え記事」判定の"判断"側に該当)。

## 種別固有 deny (機械ゲートへの追加)

| 症状 | 検知 | 処置 |
|---|---|---|
| 導入テンプレ | 「〜と思ったことはありませんか?」「本記事では〜を解説します」 | 一次体験か数字から入る |
| まとめテンプレ | 「いかがでしたか」「参考になれば幸いです」 | 最後の新情報 (残課題・次に試すこと) で切る |
| メリデメ章立ての機械適用 | 判定質問「メリット/デメリット節が結論を出さずに並べて終わるか」 | 比較したなら選ぶ。選ばないなら比較の軸を示す |
| 絵文字見出し | 見出し行頭の 🚀📝💡 | 削除。見出しは内容を指す具体句に (長文向け文章規範の見出し節を参照) |
| 公式 doc の言い換え記事 | 判定質問「公式ドキュメントに無い情報 (実測・失敗・判断) が 3 割以上あるか」→ 無ければヒット | 自分の環境の実測・詰まった点を足す。無いなら書く価値を再考 |

## 較正実例 (採点は 5 軸)

### 実例: 導入 — テンプレ疑問を実測の一撃に置き換える

**before** (14/50 → 全面書き直し):

> 皆さんは、コードレビューに時間がかかりすぎると感じたことはありませんか? 本記事では、AI を活用したコードレビューの効率化について解説します。ぜひ最後までご覧ください!

採点: 立場 3 / リズム 4 / 主体性 1 / 具体性 2 / 削減 4。機械ゲート 3 ヒット (丸投げ疑問・導入テンプレ・「活用」「効率化」)。

**after** (40/50・実測値が存在する場合):

> コードレビューの待ち時間がうちのチームは 1 PR あたり平均 26 時間あった。Claude Code を挟んで 2 時間まで縮めたので、やったことを全部書く。ただし本題は「縮めた結果、別の問題が生まれた」ほうにある。

採点: 立場 8 (「本題は別の問題」という視点の提示) / リズム 8 / 主体性 8 / 具体性 9 (26h → 2h) / 削減 7

直した点: 読者への丸投げ疑問を自分の実測に / 「解説します」の予告を「全部書く」の宣言に / 3 文目で記事の固有価値 (テンプレ効率化記事との差) を示した。
**注意: 26 時間・2 時間のような数字は実測がある場合のみ**。無い数字を作るのは捏造 (コア §6 鉄則 1)。

### 実例: 留保逃げの技術記事版 — 考慮事項は挙げたら扱い方針まで書く (provisional・n=1)

**before** (立場 3・主体性 3 → 書き直し):

> 外部連携では機密情報が漏れる可能性も考慮する必要がある。認証方式についても複数の選択肢があり、それぞれ検討が必要である。

診断: 考慮事項を疑問形で並べるだけで判断がない (コア機械ゲート #6 留保逃げに該当)。

**after** (立場 7・主体性 7):

> 外部連携ではまず顧客データが混じる呼び出しを洗い出し、該当するものは社内向けサーバーに限定する設計を既定にする。認証は OIDC を第一候補にし、要件次第で API キー方式を許容する。契約条項の適合性など法解釈が絡む論点は、断定せず法務確認を推奨するに留める (権限外領域の較正は case-report「提言の立場軸」を継承)。

直した点: 「考慮する必要がある」型の疑問並べを、扱い方針の決定 (既定にする・第一候補にする) に置換 / 権限外 (法解釈) の論点だけは断定せず「推奨するに留める」で示唆止まりにし、報告書の権限性較正が技術記事にも通ることを確認した。

## 注意

- 記事全体のワークフロー: 構成・論証を長文向けの文章規範で組む → 本 module で AI 臭と声を仕上げる、の順が速い
- 連載・シリーズ記事は隣の回とトーン・分量を揃える (コア §6 鉄則 4)
- 実在の技術類比アナロジー (例: USB-C の普及過程になぞらえた解説) は機械ゲート #20「捏造風の例え話 (例えばあなたが〜)」とは別物 — 実在の対象を使った比喩は保持する
