# Case: 仕様書・要件定義書・設計書

## 目的関数

読み手 (エンジニア / 非エンジニアの意思決定者) が「何を作るか・どう進めるか」を誤解なく掴める。実装や判断の入力として過不足がない。

## 適用

- 効く要素: H5 読み手 ◎ (**読者レベルで用語を決める** — IT 実装語・規制/法律専門語を読者次第で平易化か許容かを切り分ける)
- 殺す要素: H3 温度・H4 ムラ・H8 時間性 ✗ (report/ops-doc 同様、主張文の軸を機械適用しない)
- 採点軸: 具体性・削減・立場 (report 準拠) + 読者適合
- **読者適合の判定**: IT 実装語 (SQLite / OIDC / MFA / レスポンシブ) は読者次第で可否が変わる。非エンジニア意思決定者なら平易語へ (記録の保存 / 簡易的なログイン / スマホ対応)、エンジニアなら許容。規制/法律専門語 (分別管理・適正化法) は、定着したビジネス用語でも非エンジニア向けには平易化寄り。定着したビジネス用語 (As-Is/To-Be・進捗管理・多段階承認) は読者を問わず許容

## 種別固有 deny (機械ゲートへの追加)

ai-slop-jp §4 は「リテラル照合・判断ゼロ」が原則。**概念判断が要るものは deny でなく §5 採点へ回す**。既存 smell と重複する項目は再掲せず参照する。

| 症状 | 検知 (リテラル閉列挙) | 処置 |
|---|---|---|
| 方法論ジャーゴン | greenfield / MoSCoW / Intent 分析 / hardening / PBT / New Project / Multiple Components / 要件深さ Standard / opt-in / opt-out / MVP (実データ出現語の閉列挙・「等」で開かない) | 平易語へ (新規開発 / 優先度 / 目的分析 / セキュリティ強化 等)。読者を問わず排除 |
| 生成過程メタ | v3 / 改訂履歴 / Round 1 反映 / 要件深さ / A1〜A7・U1〜U3・KR#/F# 等の記号+ハッシュ+番号 ID・light ADR・内部ラベル | 削除。版管理は文書外 (git/履歴表) へ。記号 ID は平文の確認事項へ |
| 内部呼称・内部メタの成果物混入 | 内部ワークスペース名 (プロジェクト固有の作業領域名等) / 作業トラック名 / 内部略語 (プロト・モック・ramp 等) / **ファイル名・パス** (社内の一時ファイル名・保存先パス等) / **内部出所符号・参照記号** (④・③④・KR#1・A1〜 等) を成果物 (提案書・スライド・注記/出所・公開ドキュメント) に転記 | 案件・成果物の実体を表す表現へ (出所は「机上試算」等の性質表記に留め実体ファイルは資料外へ)。**対外に限らずデフォルトで入れない** — 例外は個人使用の文書 or 読み手と共有済みの参照のみ (「内部メタデータは成果物にデフォルトで入れない」という判断軸に従う: メタデータか / 共有済みか / 個人用途かの 3 問で判定する)。ワークスペース名等の内部符号が外部ツールへの入力に混入していないかは、可能であれば投稿前チェックの仕組みで別途検知する |
| IT 実装語 (検知のみ・処置は読者判断) | SQLite / OIDC / MFA / レスポンシブ (閉列挙) | **フラグ立て**: 読者を確認し、非エンジニア文書なら平易化 (記録の保存 / 簡易的なログイン / スマホ対応)。読者依存の可否判定は §5 採点・H5 に委ね、deny では検知のみ |
| 未検証の断定 | 「〜より安全」「〜が効率的」等の比較優位フレーズ (リテラル) | 「〜という仮説」「検証中」に。根拠有無の判定は照合者に委ねず、フレーズ検知に留める |

**本体 §4 から継承 (再掲しない・参照で足りる)**: #21 見出し・ラベルへの説明句詰め込み / #6 留保逃げ・断定回避の裏返し / #16 文末単調 (ですます調の混入もこれで拾う → 常体・体言止めへ)。

## 較正実例

以下は架空の要件定義書 (サブスクリプション決済システム) を非エンジニア読者 (業務担当・双方の部門長) 向けに校正した逐語の before/after。

### 実例 1: 方法論ジャーゴンと生成過程メタの削除

**before** (requirements.md の §0):

> Intent 分析 / 要求タイプ New Project (greenfield) / 要件深さ Standard

採点: 具体性 2 (何を作るか無い) / 削減 1 (用語が本文でない) / 立場 1 (何も言っていない)。機械ゲート 3 ヒット (Intent 分析・greenfield・要件深さ Standard)。

**after** (stakeholder 版):

> セクションごと削除し、§1 目的に以下を配置:
> 「支払先を追加するときの承認を、申請から承認、カード会社への依頼まで一つの流れで扱えるように」

採点: 具体性 8 (誰が何をするかが見える) / 削減 8 / 立場 7 (目的が明確)

### 実例 2: 未検証の断定を仮説に置換

**before** (requirements.md):

> 『手動運用より、クレカ + 承認の方が安全 × 楽』という仮説

**after** (stakeholder 版逐語):

> 『手作業より安全で楽になる』という見立ては…確かめている段階

直した点: 「クレカ」を平易語「手作業」に / 「仮説」を「見立て」「確かめている段階」へ言い換え (非エンジニア向け)。

### 実例 3: 構造再編 (ID 体系の全廃・表の圧縮)

**before** (requirements.md の FR 表):

> FR-1〜11 の ID 付き詳細表 (「プロトの作り込み」列付き・13 個のテーブル)

**after** (stakeholder 版):

> ID なし・機能名 + 説明の 2 列表「必須機能の一覧」に圧縮。NFR-1〜7 を含む 13 個のテーブルを「必須機能の一覧」「満たすべき条件」の 2 表に畳んだ。

採点: 削減 9 (項目数は不変・ID と詳細列を削ぎ落とし) / 具体性 8 (機能名は残る)

### 実例 4: フレームワーク過大 — 案件規模に対する枠組みの過大さ (provisional・n=1)

**before** (内部 15-25 名向け社内ツールの要件定義):

> ## Market Segment
> 対象は社内のコスト管理担当者 (15-25 名)。
> ## Jobs-to-be-Done
> 「コストの異常を素早く検知したい」というジョブ。
> ## Value Proposition Canvas
> Pain: 手動集計に時間がかかる。Gain: リアルタイム可視化。
> ## North Star Metric
> KR#1: 月次レポート作成時間を 50% 削減。

採点: 具体性 3 (ツール規模に対しフレームワークが過大) / 削減 2 / 立場 4。判定質問「この規模の内部ツールに Market Segment・JTBD・Value Proposition Canvas・North Star Metric が要るか」→ no。

**after**:

> ## 目的
> コスト異常の検知にかかる手動集計の時間を減らす。
> ## 利用者
> 社内のコスト管理担当者 (15-25 名)。
> ## 課題
> 月次レポートの作成に手作業の集計が時間を取っている。

採点: 具体性 8 / 削減 8 / 立場 6

直した点: PMF/PRD 系フレームワーク (Market Segment・Jobs-to-be-Done・Value Proposition Canvas・North Star Metric・バリューカーブ・OKR) を全廃し、案件の複雑度に応じて項目を採否調整するという考え方に従って、素直な見出し (目的/利用者/課題) に畳んだ。記号 ID (KR#1 等) も上表の生成過程メタ deny に該当するため削除。

**provisional (n=1)**: 内部小規模ツール 1 件の較正のみ。「過大」の判定基準 (対象人数・予算等の閾値) は未確定 — 次の類似案件で確定させる。判断は本実例に照らして行い、deny 化はしない。

## 注意

### 隣接種別との境界

- **report との境界**: 判断材料の事実提示 = report / 作るもの・進め方の仕様定義 = spec-doc。採点軸が report と同一 (立場・具体性・削減) のため、境界は目的関数で切る。
- **ops-doc との境界**: 作業手順 = ops-doc / 要件・設計仕様 = spec-doc。

### 確認事項アノテーション

未確定・未回答事項は note ブロックで可視化し、本文に曖昧に埋めない。記号 ID (A1/U1 等) は付けない (生成過程メタのため)。

### 2 読者版を持つ場合

engineer 版と stakeholder 版の両方を持つ場合、仕様事実 (承認順・項目・状態遷移) の齟齬を検出し同期する責務は文書全体の生成プロセスが担う (本 module は文体・用語のみ)。
