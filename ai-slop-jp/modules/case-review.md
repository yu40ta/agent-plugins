# Case: レビューコメント (PR/issue のレビュー指摘・返信)

## 目的関数

レビュイーが「何を・なぜ・どう直すか」を迷わず掴め、修正要否 (prefix の温度) が一致している。指摘そのものと根拠だけを書き、レビュー基準の内部事情は出さない。

## 適用

- 効く要素: H1 立場 ○ (prefix で温度明示) / H5 特定の読み手 ◎ (レビュイー) / H7 省略と余白 ○
- 殺す要素: H2 体験・H3 温度・H4 ムラ・H8 時間性 ✗
- 採点軸: 立場・具体性・削減。平均 7.0 未満は書き直し
- **棲み分け**: prefix 選定 (`[ask]`/`[want]`/`[info]` 等、温度を表すラベル体系)・構造テンプレ (背景 → 具体的なアクション)・読み手のレベルに応じたトーン調整は、レビューコメント全体の型を定める別のガイドラインが主管する領域とし、本 module は AI 臭の機械ゲートのみを担って二重管理しない。基本姿勢: 指摘そのものと根拠を示し、prefix で温度 (要修正か・確認か・補足か) を先頭で明示する

## 種別固有 deny (機械ゲートへの追加)

| 症状 | 検知 | 処置 |
|---|---|---|
| 安心材料の重複 | 判定質問「同趣旨の安心材料・否定 (『〜と安心です』『〜していると安心です』『〜必ず直す必要はありません』等) が 1 レビュー内で 2 箇所以上あるか」→ yes ならヒット (case-ops-doc の同名項目に揃える) | 効かせ所 1 箇所に集約する |
| 願望形の連鎖 | 「〜したいところです」「〜おければと思います」「〜と安心です」の願望・希望表現の近接連鎖 (同段落・連続コメント内) | 1 つを断定/依頼の言い切りに |
| 過剰敬語・冗長敬語 | 文字列: 「でしたでしょうか」「ますでしょうか」「ご意図」「ご想定」等の二重敬語・冗長敬語 (主観動詞・願望形とは別軸で、敬語の重ね掛けそのものが対象) | 「でしょうか」「意図」等に簡潔化。部下・同僚レビューでは特に冗長 (相手との関係性で敬語量を調整する、という定性的な指針に対し、本 deny は文字列レベルのゲートを担う) |
| 主観動詞の近接 | 「〜と感じました」「〜が気になりました」が同段落に併存 | 事実として言い切れる方は断定に寄せる (§4 #6 留保逃げと接続) |
| 称賛の目的化 | 「素晴らしい」「すごく良い」等をコメントの主目的にする | 事実評価に留める (指摘そのものと根拠だけを書く、という基本姿勢に接続) |
| approve 示唆の先取り | 「LGTM」「approve 方向で問題ない」をレビューのみ (COMMENT) 段階で書く | 削除 (指摘そのものと根拠だけを書く、という基本姿勢に接続) |
| レビュー基準のメタ露出 | 「対象: シニア」「整合性をしっかり確認しました」「体裁のみ確認」等、自分が依拠した skill・観点・自己宣言 | 削除。指摘そのものと根拠だけを書く |
| 前置きの枕 | inline の冒頭に「〜は良い整理だと思います」等の前振りを置く | `[prefix] 一文要約` から本題に入る |
| 砕けすぎ・絵文字過多 | 過度な口語 (「含めちゃうのがきれい」等) や装飾絵文字 | 削除。絵文字は最小限のショートコードのみ |
| 能動観測宣言 | 文字列: 「〜と読み取りました」「〜と読み取れました」「〜と読みました」「〜と受け取りました」「〜と把握しました」(能動動詞 + "ました" 終止で自分の観測行為を宣言する型。声のプロファイルが許容する「〜と読めます」「〜と見受けられます」等の状態的表現とは別物) | 「〜と見受けられます」「〜と読めます」「〜のように見えます」等の状態表現に置換。事実の断定で足りる箇所は宣言を削る |
| 冗長修飾 | 文字列: 「明示的に織り込みたい」「〜の出発点として問題ない」「〜として過不足なく揃えている」「〜として問題ない」 | 短く言い切る (明示したい / 揃っている / 仮案として問題なさそう) |
| 内部略語・造語 | 判定質問「レビュー文内に、対象文書に無い自家製略語・造語・単語の勝手な切り取りが入っていないか」(実例: 「4M/3M」(4 ヶ月/3 ヶ月)・「対象側課長」・「ガント」(略称)・「見立てのブレを吸収」・「早見」(「早見表」の切り取り)) | 対象文書に載っている語 (プロダクトチーム側の担当課長・スケジュール図・4 ヶ月/3 ヶ月・早見表) を使う。抽象化した造語・単語の一部切り取りは削除 |
| 文書外の実担当者名の持ち込み | 判定質問「レビューコメント内で、対象 PR 本文・関連ドキュメントに書かれていない実担当者名 (人名) を挙げていないか」(例: assessment の respondent や別文書で見た人名を、関与計画書のレビューに勝手に持ち出す) | 対象文書に載っている役割名 (「Embedded SRE 担当」「プロダクト側インフラ運用担当」) までで止める。人名は対象 PR で確定した場合のみ引用する |
| 構文ミスマッチ | 判定質問「事実を述べる知覚・観察の述語 (『読める / 読み取れる / 見える / 感じる / 考える / 見受けられる』の活用形) を条件節・接続節にし、主節に主観述語 (『〜と感じました / 気になりました / リスクを感じました / 心配です』の活用形) を接続していないか」→ yes ならヒット。接続の形式は問わない (と / ので / から / ば / なら / たら)。**根拠**: 事実観察 + 主観という二重の心的操作を無理に条件-結果でつなぐと、ニュアンスが破綻して回りくどくなる | 条件節を切り離し、事実観察と主観結論を独立させる (「〜のように読める。〜のリスクがある」) |
| 論拠の散文化 | 判定質問「1 コメント内の背景・理由が 3 文以上の散文で書かれていて、結論 + 箇条書きに再構成できるか」→ yes ならヒット | 冒頭 1 文で結論、以下を箇条書きに |
| 動作述語 + 「提案です」直付け | 判定質問「動作を示す述語 (連用形『しやすい』/ 可能形『減らせる』/ 動詞終止形『吸収する』 等) の直後に、間を置かず『提案です』『アイデアです』『方針です』を直付けしていないか」(実例: 吸収しやすい提案です / 減らせる提案です / 統一する提案です) | 「〜すると〇〇できるように思いますので、提案です」等、動作の結果 (「〜するように思います」「〜できます」) と提案表明を句点や接続助詞で分ける |
| 「仮案」の温度誤り | 判定質問「本レビューで話者本人が新たに出す提案・叩き台を『仮案』と呼んでいないか」(対象 PR 内で既に『※仮案』と付いた項目を引用する場合は対象外) | 「ドラフト」「叩き台」「提案」に置換。稟議感を出さない |
| 抽象化した指摘・具体を出さない指摘 | 判定質問「指摘の『具体的なアクション』が『〜の位置付けを分ける』『〜を明示する』等の抽象動詞で終わっており、レビュイーが読み返しても *どのチャネルで誰にどうする* かの具体像を作れないか」→ yes ならヒット (実例: 「エスカレーションパスを平常時と障害時で分けたい」) | 5W1H (誰が / どのチャネルで / どう連絡・記載) の穴を埋める。連絡ルート系は @mention 先・チャネル名・応答期待時間・2 次エスカレーション先の 4 要素が最低ライン |
| 造語熟語・ジャーゴン | 判定質問「現場・ビジネス会話で自然に使われない、抽象語を接ぎ木した圧縮名詞句が入っていないか」(実例: ゲート・完全整合・整合が完全に取れている・未確定担当・横断決定・帰属・宙ぶらりん・集計主 KPI)。**「完全〜」「未〜」「〜済」「〜性」「〜化」「〜化済」「〜先」等の抽象接尾辞・接頭辞で名詞を作った圧縮語は本項を疑う。分解して自然な業務日本語で言えないかを毎回試す**。既に定着した業務語 (追加起票・整合性・担当・承認) は対象外 | 平易な動詞・状態記述に展開する (未確定担当 3 件→担当が決まっていない 3 件 / 完全整合・整合が完全に取れている→整合性◎・plan とかみ合う / 宙ぶらりん→「主導がどちらか決まらない」/ 集計主 KPI→集計のメイン KPI / 横断決定→両者で共有する決定事項 / 帰属→どちらの側で持つか) |
| 漢字連続の圧縮名詞句 | 判定質問「4 文字以上の漢字が助詞なしで連結、または `〜時の〜〜`・`〜条件〜`・`〜結果〜`・`〜作業`・`〜処理`・`〜格納`・`〜確認`・`〜判定` 等の抽象名詞後置で漢字塊が並んでいるか」(実例: 注入予兆検知時の退避トリガー / 集計主 KPI / 予兆検知の帰属 / 確信度不足時の退避判定 / 意図分類結果格納 / 境界条件確認作業)。**免除**: 対象 PR/issue/plan 本文で既に定義・多用されている業務語 (例: 会話全体単位・意図分類ラベル・確信度スコア) はレビュー側でも同表記で引用してよい。**この免除は機械判定する** — 対象ファイルを取得して同表記を grep し、0 件なら免除不成立 (「読み手の職種にとって既知か」の主観判断ではない) | 動詞句に展開する (「インジェクションの兆候を見つけたら OP に退避する」/「集計のメイン KPI」/「兆候を見つける役目をどちらの側で持つか」/「確信度が足りないとき退避する」/「意図分類の結果を保存する」/「境界条件を確認する作業」) |
| 回りくどい否定・思考動詞 | 判定質問「単純断定で言い切れる箇所を、受動連結や思考動詞で断定を弱めていないか」(実例: 起票に含まれていない・保てると考えている・読んでいます・理解しています・該当節・plan で確定済みの決定を issue に反映してもらう趣旨)。**対象は「断定できる事実」をぼかした場合に限る** — 断定できない解釈を留保した表現は本項の対象外で、その反復は語彙選択の観点 (平板化も避ける、という別の指針) が扱う (留保を保ったまま語彙を変える処置になり、本項の「断定に戻す」とは逆方向。適用は本項 → その指針の順) | 単純断定に戻す (起票に含まれていない→起票されていない / 保てると考えている→保てる / 該当節→対応箇所 / 「〜と理解しています」→削除して事実断定) |
| 指示語の遠隔参照 | 判定質問「指示語 (それ / これ / そちら / 該当) の直前 1 文以内に指示対象がなく、複数候補があってどれを指すか一意に決まらない箇所があるか」 | 具体名で書き直す (「それに準拠する」→「#8 が先に出した JSON スキーマにあわせる」) |
| 略称の単独使用 | 判定質問「略称 (I/F・API・MTG・SSOT・NP・SoR 等) が節の初出で使われ、**同一文内に括弧書きの正式名補記または平易語言い換えが無い**か」。プロジェクト全体で定着済み (design-doc 冒頭に定義済み等) は対象外 | 補記するか平易語に置換する (「I/F (インターフェース定義)」/ さらに略称を使わないなら「受け渡しの契約」) |
| 本人名の括弧書き自称 | 判定質問「本人名義のレビュー・コメントで自称『私』に本人名を括弧書きしていないか」(実例: 私 (田中) が別 PR で反映) | 「私」または「私の方で」に短縮 |
| 場違いカタカナ英語 | 判定質問「業界・ビジネス文書で日本語の的確な語がある場面のカタカナ英語がヒットしていないか」(実例: サイン (兆候)・タスク (作業)・ピンポン (往復)) | 日本語の的確語に置換する (サイン→兆候) |
| 総評での主観動詞ゼロ | 判定質問「全体レビュー・親追跡の総評で『〜と感じました』『〜と考えます』等の立ち位置表現が皆無で、平叙断定のみで押し切っていないか」→ yes ならヒット (無機質になる) | 総評導入・判断根拠に 1〜2 箇所だけ主観動詞を自然な範囲で挿入する (願望形の連鎖 deny と両立するよう連発しない) |
| 見出しの口語化 | 判定質問「`[prefix] タイトル` のタイトルが平叙文 (述語で終わる) または口語 (『〜と思いました』『〜が気になりました』『〜ではないか』) か」→ yes ならヒット | 端的な体言止め (目安 15〜25 字) に削ぎ落とし、思考・所感は本文へ (見出しは対象を指す体言止めに、所感は本文に置くという構造テンプレの指針に接続) |
| 仮想将来場面の持ち出し | 判定質問「レビュー本文・総評・サマリのいずれかで、未確定の将来場面を**条件節または目的節**に置いて記述の存在意義を正当化していないか」→ yes ならヒット。接続の形式は問わない (〜あれば / 〜ときのため / 〜場合に備えて / 〜することがあれば / for future reference)。実例: 「9 月以降にこの数字を引く場面があれば」「後から数字を引くときのために」「将来的に必要になったときのため」。**補足であることは prefix (`[info]`) が既に示しているため、読み手の将来行動を想定して見せる必然がない**。**対象外 2 種**: ① 確定した仕様・事実から導かれる因果予測 (「証明書は 2026-09-30 で失効するので 9 月末に停止します」) — 指摘の中身そのものであり hedge ではない ② アクション指示節の業務時制 (「今後の運用手順として README に追記してください」) — 指摘の存在意義ではなく実施範囲を限定している。**ヒットの要件は「記述の存在意義を将来場面で正当化しているか」**で、将来時制であること自体ではない | 仮想場面を削り事実を直接書く (「現時点の実効単価は 0.4 倍です」)。補足の理由を書くなら、想定場面ではなく確定した事実 (管掌の所在・出所の違い) を示す。**横断型のため他書種でも成立する** (仕様書の「将来拡張時に必要になれば」・運用文書の「今後参照することがあれば」等) — smell-catalog の時間性演出系と同系だが、実損がレビューで出たため当面は本 module が判定を持つ |
| 内部運用メタの混入 | 判定質問「レビュイーの作業に無関係な内部運用メタ (merge の実行主体・repo の運用区分・承認フローの内部事情) を投稿本文に書いていないか」(実例: 「team repo のため merge はレビュアー/私の手で行います」「approve/merge はレビュアー判断に委ねます」)。**「レビュー基準のメタ露出」が依拠 skill・観点の自己宣言を対象にするのに対し、本項はレビュー結論の運用・実行主体を対象にする**。merge 主体・repo 区分はレビュイーが知る必要がなく、投稿本文に出る必然がない | 本文から削る。merge 可否・承認フローは投稿先の運用 (自分の判断メモ) であって、レビュイーへのコメント本文に書かない。**投稿前にこの定型句が本文に混ざっていないか機械的にチェックする運用を推奨する** (自動化していれば、それを一本化した投稿経路に組み込む) |

## 較正実例 (採点軸: 立場 / 具体性 / 削減)

### 実例: 変数名の指摘 — 称賛と願望形を削減し断定に

**before** (平均 3.7 → 書き直し):

> すごく良い整理だと思います! ただ、この変数名 `data` は少し気になりました。もう少し具体的な名前にできればと思います。例えば `userData` とか `accountData` にすると安心です。他の箇所でも同じパターンが見られたので、統一できると安心です。

採点: 立場 4 (「できればと思います」の願望止め) / 具体性 4 / 削減 2 (称賛・願望形・安心材料の重複)。機械ゲート 4 ヒット (称賛の目的化・願望形の連鎖・安心材料の重複・前置きの枕)。

**after** (平均 7.7):

> [want] 変数名 `data` を具体化する
>
> ### 背景
> 現状の `data` は型情報がなく、L45・L72 でも同じ汎用名が出ており、スコープをまたぐと追いづらくなります。
>
> ### 具体的なアクション
> この変数が保持する内容に応じて `userData` (ユーザー情報) または `accountData` (アカウント情報) に変更してください。L45・L72 も同様に変更すると一貫性が保たれます。

採点: 立場 8 (`[want]` で温度明示・修正依頼を言い切り) / 具体性 8 (該当行 L45・L72 を明示) / 削減 7

直した点: 称賛の前置き削除 / 願望形 (「できればと思います」) を依頼の言い切りに / 安心材料の重複 (2 回) を 1 箇所に集約 / prefix で温度を明示。

### 実例: エラーハンドリングの指摘 — 主観動詞を事実の断定に

**before** (平均 4.0 → 書き直し):

> エラーハンドリングが気になりました。ここで例外が発生すると感じました。try-catch を追加したいところです。

採点: 立場 3 (「したいところです」の願望止め) / 具体性 5 / 削減 4。機械ゲート 2 ヒット (主観動詞の近接・願望形の連鎖)。

**after** (平均 8.0):

> [want] エラーハンドリングを追加する
>
> ### 背景
> L34 の API 呼び出しで例外が発生した場合、処理が中断され呼び出し元にエラーが伝わりません。
>
> ### 具体的なアクション
> L34 を try-catch で囲み、catch ブロックでログ出力とデフォルト値の返却を行ってください。

採点: 立場 8 / 具体性 8 / 削減 8

直した点: 主観動詞 (「気になりました」「感じました」) を事実の断定 (「例外が発生した場合、〜伝わりません」) に置換 / 願望形 (「したいところです」) を依頼の言い切りに。

### 実例: 散文の背景・理由を結論 + 箇条書きに

**before** (平均 4.3 → 書き直し):

> [want] 伴走 4M → 自立推進 3M の遷移タイミングをキックオフで見立て直す余地を明示
