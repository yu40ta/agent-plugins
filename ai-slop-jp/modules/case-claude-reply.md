# Case: Claude 応答 (完了報告・調査報告・受領・recap・insight)

## 目的関数

出力内容を構造で理解できること。読み手が文を目で追わなくても、見出し・key-value・箇条書きの構造だけで状況を掴める。

## 適用

- 効く要素: 構造化そのもの (H 群の「声」ではなく、読み手が構造で追える設計)。H5 特定の読み手 △ (読み手はユーザー本人・厳密な想定読者設定は不要) / H7 省略と余白 ○ (短い受領は最小限でよい・C8 完結強迫を強く適用)
- 殺す要素: H1 立場の劇的表明・H2 一次体験の演出・H3 温度・H4 ムラ・H6 声の飾り・H8 時間性の演出は全て ✗。感情の起伏や決め台詞で「ちゃんと書いてる感」を出すのは C6 の典型 (下記の deny 表を参照)
- 採点軸: 具体性・削減・構造。平均 7.0 未満は書き直し
  - **構造軸**: 見出し・key-value・[LABEL]・箇条書き文法が目的関数どおりに機能しているかを問う軸。他 case module の「リズム」相当をこの module では「構造」に置き換える (Claude 応答は音読前提でなく一覧性前提のため)

## フォーム型 (既定の型)

- h2 見出しでセクションを区切る。短い報告でも可。見出し自体を結果の体言止めにしてよい (「## スナップショット保存完了」)
- **1 見出し = 1 トピック**。1 つの見出しに 2 つ以上のトピックを詰め込まない。「A と B」のような連結見出しはこの違反の典型症状
- 結果は体言止めの一文で示す (「スナップショット保存完了」)
- データは `key: value` 行で示す。**キーは英小文字の定型語で統一する** (`path` / `status` / `created_at` 等)。カタカナラベル (「ステータス」「作成:」) と混在させない。値内の注記は英語可 (`approve by user`)
- 箇条書きはプレーンな短ラベル (ラベルを太字にしない)。子項目はネストで従える
  - **太字はキー事実に効かせるのは可** (例: 「**local main は origin より 2 commit 遅れ**」)。NG はラベルの太字化と乱発。全太字排除は過剰検知
- 判定・裁定を書くときの箇条書き文法: `[LABEL] 対象: 結論｜具体`。結論を先に短く、詳細は「｜」の後に置く
- 状態は行頭の `[LABEL]` でラベリングする。ラベルは英語のみ・英大文字で統一 (`[OK]` `[NG]` `[SKIP]` `[EXEC]` `[WIP]` `[DONE]` `[READY]` `[WARN]`)。日本語ラベル・小文字ラベルは使わない
- 参照番号は種別を明示して詰める: `issue#154`・`PR#232` (裸の `#154` は禁止)。**GitHub の機能構文 (`Closes #154` 等) はそのまま維持する** — close キーワードとして機能する文字列のため、種別付き表記に変換しない
- 代替・並記は「A / または B」のスラッシュ表記
- 確認・許可を求めるときは判断理由を必ず添える (説明責任)。「進めてよいですか?」の単純確認は避け、「〜のため、この手順で進めます。問題なければこのまま進めます」の形にする
- 受領の既定は「OK です」「承知です」の短形。「承知しました」「かしこまりました」等の定型活用形は使わない
- 発見・解釈のような複数論点の報告は、途中経過でも見出し (症状 / 原因 / 次の確認 等) + 箇条書きで構造化する。短い受領応答のみ見出しなしでよい
- エンジニア語彙 (stale・未取込・local main 等) はそのまま使ってよい (下記「過剰検知の境界」を参照)

### 途中経過報告 (WIP) のパターン

処理中の状態を報告するときは以下の型に従う:

```
## [WIP] adversarial-review-loop: round 1 (background)
独立の opus subagent 4 体が別々の観点でレビュー中
1. 上位文書 ${file_name} との整合性
2. 〇〇の実行可能性
3. 機微の安全性
4. 移行データ漏れの有無

## 完了後の流れ
FB を一次情報で確認 -> 採否の決定 -> 計画への反映 -> Critical が残れば round 2
```

- 見出し先頭に `[WIP]` 等の状態タグ + **処理の実名 (skill 名・コマンド名) + フェーズ + (background)**
- 観点・項目は番号リストで、対象は `${file_name}` 等の実名で埋める (抽象化しない)
- 「整合性」「実行可能性」等の定着した技術語は複合語でも可。NG は「上位文書整合性」「移行データ完全性」のような自家製連結圧縮 (助詞を入れて分けるか、結果で言う)
- 今後の手順は「完了後の流れ」のような独立セクションへ分離する

## 種別固有 deny (機械ゲートへの追加)

C1/C6/C7 系の一般 deny (自家製漢語ジャーゴン・動詞句の複合名詞化・名詞圧縮スタックの参照・発見の自己劇化・謝罪/誠実の口上・場面転換ナレーション・プロセスの俗語擬人化/医療メタファー・使役ぼかし/方向ぼかし・二人称「あなた」・英語断片の混成名付け・メタ自己言及ラベル) は `smell-catalog.md` の C1/C6/C7 に追加済み。本表は Claude 応答に固有の構造・表記症状のみを扱う。

| 症状 | 検知 | 処置 |
|---|---|---|
| 「A と B」連結見出し | 判定質問: 見出しが並列助詞 (と・および) で 2 つ以上のトピックを連結しているか | 見出しを分割し 1 見出し 1 トピックにする |
| key の日本語ラベル | 文字列: 「ステータス:」「作成:」等のカタカナ・和語キー | 英語キーへ (`status` / `path` / `created_at`) |
| 裸の参照番号 | 文字列: 種別なしの `#154` 単体 (GitHub 機能構文の `Closes #154` を除く) | `issue#154` / `PR#232` の種別付き表記へ |
| 絵文字判定 | 文字列: ✅❌⚠️🎯 等の判定絵文字 | `[OK]` `[NG]` `[WARN]` `[DONE]` `[READY]` の英大文字ラベルへ |
| AI 定型の受領 | 文字列: 「承知しました」「かしこまりました」 | 「OK です」「承知です」の短形へ |
| 口語イディオム | 文字列: 「羽目になりました」等の口語慣用句 | 使わない。事実を直接書く |
| 理由なき確認要求 | 判定質問: 確認を求める文に判断理由が添えられているか → 添えられていなければヒット | 「〜のため、この手順で進めます」と理由を添える |
| ラベルの裸提示 | 判定質問: セッション内ラベル (H0・M2a 等) に中身の一言が添えられているか → 添えられていなければヒット | 「H0 (辞書スコープの仮説)」のように括弧で概要を付ける |
| 自己評価の言い切り | 判定質問「自己検証・振り返り等のセクションで、方法の記述でなく結果の自己評価 (『正確な指摘を行った』『適切に対応した』) を書いていないか」→ yes ならヒット | 方法の記述に置換する (例: 「正確な指摘を行った」→「最新仕様と照合した」)。セクションの存在自体が必須でも中身の語彙は対象 |
| 技術語の過剰和訳 | 判定質問: 英語のまま流通している技術語を日本語に訳し下げていないか (`background`→「背景」/ `raw value`→「生値」/ `stale`→「陳腐化した」等) → yes ならヒット | 英語表記を保持する (「バックグラウンドで実行中」「raw 値」)。上記「エンジニア語彙は保持」の裏返し — 保持すべき語を訳すのも同じ違反 |
| 状態を含まない見出し | 判定質問: 体言止め見出しが「完了した結果」か「これからやる作業」か、見出しだけで判別できるか → 判別できなければヒット | 状態を含める (「後片付け」→「後片付け完了」/「後片付け残」)。作業種別だけの見出しは読み手に状態を推測させる |

## 較正実例 (採点軸: 具体性 / 削減 / 構造)

### 実例 1: スナップショット保存完了報告 — 確定稿 (FB 7 回)

診断で処置した症状 (版を重ねるごとに):
- 地の文への平文化 → 誤り (この文書種はフォーム型が既定であり、構造化を崩す方向の修正だった)
- ジャーゴン (退避・従属・純化) → 日常語に言い換える
- 「A と B」連結見出し → 分割
- 1 見出し 1 トピックの徹底
- メタ自己言及ラベル (「書き残した判断」) → 対象そのものを指す体言 (「記録内容」) へ
- 「再裁定」「送った」の内部工程メタファー → 見直し・実装計画に回した、へ
- key ラベル「ステータス」→ `status`

**確定稿**:

```
## スナップショット保存完了
path: notes/outputs/context-snapshot-2026-07-17-session-context-sharing.md
status: spec v2 収束、ユーザーレビュー待ち (git 変更なし)

## 記録内容
- 見直した設計 3 件とその理由 (topics/ 撤回・snapshot 存続・tasks.md をタスク専用に絞る案の撤回)
- hook を件数のみ出力にした理由
- 実装計画に回した 5 件 (§11)

## 再開
snapshot 末尾の指示文を参照 / 判断待ち事項の台帳にも記録済み (「なんやったっけ」で復元可能)
```

読み取れる規則: h2 体言見出し 3 分割 (結果 / 記録内容 / 再開) / `path:` `status:` の英語キー / 箇条書きはプレーンラベル / メタ自己言及ラベルの排除。

### 実例 2: 3 候補から推奨を選ぶ応答 — 確定稿 (FB 2 回)

診断で処置した症状:
- 初回診断で除去: 「正直に選ぶと」の口上 (謝罪・誠実の口上系と同族の演出) / `signal` のような英語断片ジャーゴン
- FB 1: ラベルは英大文字のみに統一 (`[SKIP]` `[EXEC]`。日本語ラベルは禁止)
- FB 2: 判定の箇条書き文法を `[LABEL] 対象: 結論｜具体` に統一 / 受領は「承知です」に統一

処置後の骨格 (型のみ・全文ではない):

```
[EXEC] 候補A: 採用｜理由は〜
[SKIP] 候補B: 見送り｜理由は〜
```

読み取れる規則: 口上は演出であり中身に寄与しない → 削除して結論から入る / ラベルは英大文字体系に統一 / 箇条書きは「結論｜具体」の 2 段構成。

## 過剰検知の境界 (deny でも処置しないケース)

- **エンジニア語彙は保持**: stale・未取込・local main 等の英語/git 短縮語は日常語化しない (過剰検知)。NG は文語・文学調 (謳う→記載された・公算→可能性) や俗語擬人化 (死ぬ・飛ぶ→失敗する・スキップされる) との混同
- **ユーザー運用語は保持**: gotcha・タスク化・issue 化・自動化のようにユーザーが明示的に運用している語は自家製ジャーゴンではない (共有語彙の判定基準: Claude が勝手に作った語だけがジャーゴン)
- **慣用比喩は保持**: 地続き・建前・残骸のような一般的な慣用表現は自家製メタファーではない
- **効かせ所の太字 1〜2 箇所は保持**: キー事実への太字は残す。NG はラベルの太字化と乱発
- **構造マーカー (見出し・箇条書き・表) は既定**: 「箇条書き逃げ」(smell-catalog C6) をこの文書種に適用しない。短文書への見出しも過剰検知としない
- **絵文字判定 (状態→[LABEL]) と見出し末尾のテーマ絵文字 (smell-catalog C6) は別物**: ✅❌⚠️ 等の状態絵文字は `[OK]`/`[NG]` へ変換 (既存規則)。一方、リスト項目末尾に内容連動の単発絵文字を並べる演出 (🔤🏗️🗺️ 等) は用途を問わず削除 (両方とも Claude 応答では NG)

## 注意

- 本 module は「Claude が生成する応答」全般を対象にする点で他 case module と異なる (書き手が Claude 自身)。声のプロファイルは本人名義文書向けのため、本 module では読まない
- 短い受領応答 (「OK です」で完結する場合) は見出しなし・最小限でよい。ユーザーの用語を自分の文で再掲しない。次のマイクロステップの実況 (「まず本文をファイル化します」) は書かない
- 予告 (「次のメッセージで推奨を出します」) は対話全般で slop。その場で出すか、最小の問いで終える
