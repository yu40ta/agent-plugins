# Case: 運用文書 (運用ルール・マニュアル・手順書・全体周知)

## 目的関数

読み手が迷わず・間違えず・最短で動ける。**書き手の声は出さない**。

## 適用

- 効く要素: H5 特定の読み手 ◎ — ただし文体ではなく**読み手への想像力**として現れる: 作業者の文脈に沿った順序、つまずきの先回り、例外の明記
- **殺す要素: H1 立場・H2 体験・H3 温度・H4 ムラ・H6 声・H8 時間性は全て ✗**。過去、運用周知に主張文の軸 (煽りフック・運営の心情) を機械適用して却下された。この文書種に「書き手」は要らない
- 採点軸: 具体性・削減・リズム (読みやすさ)。平均 7.0 未満は書き直し
- 表記: 和欧間スペース・全角半角などの表記ルールはここで一番効く

## 種別固有 deny (機械ゲートへの追加)

| 症状 | 検知 | 処置 |
|---|---|---|
| 勧誘・意気込み調 | 「ぜひ〜しましょう!」「チーム一丸となって」「より良い〜を目指して」 | 削除。運用文書に決意表明は不要 |
| 絵文字・顔文字 | **単発を含む全て** (catalog の一般則「行頭連続のみ」より厳格) | 削除。周知に温度は不要 |
| 目的の後置き | 判定質問「対象者と変更点が最初の 2 文に入っているか」→ 入っていなければヒット | 対象 → 変更点 → 期日 → 手順 → 問い合わせ先の順に組み直す |
| 【重要】乱発 | 1 文書に 2 個以上 | 本当に事故る 1 箇所だけに絞る (全部重要 = どれも重要でない) |
| 曖昧な主体 | 「〜される想定です」「〜となります」 | 誰が何をするかを主語つきで書く |
| 網羅の未整理 | 例外・補足が本文に混ざり込む | 本流の手順を先に完結させ、例外は別ブロックに分離 |
| 安心材料の重複 | 判定質問「同趣旨の否定・安心材料 (『〜する必要はありません』等) が複数箇所で繰り返されているか」→ yes ならヒット | 1 箇所に集約する |
| 寄り添い表現の乱発 | 文字列: 「一緒に」「寄り添って」等が 3 箇所以上 | 効かせ所 2 箇所までに絞る |
| 太字乱発 | 判定質問「太字強調が『誤ると手戻り・事故』系統以外にも多数付いているか」→ yes ならヒット (目安: 文書全体で 12 箇所超) | 「誤ると手戻り・事故」の系統だけに絞る |
| 期日の緩和語 | 文字列: 「無理のない範囲で」「可能な範囲で」(期日そのものを弱める用法) | 削り、例外条件の手順 (対象外・猶予ルール) に置換 |
| 下記参照の曖昧化 | 判定質問「『下記』の指示先が具体の操作 (手順番号・見出し名) でなく漠然と下方全体を指しているか」→ yes ならヒット | 「手順 3 を実施」等、操作名で指す |
| 職種ジャーゴン | 文字列: イネーブルメント (読み手に非エンジニアが混じる場合) | 支援・伴走等の平易語に開く |
| 比喩+包み紙 | 文字列: 「ものさし」「〜の取り組みを始めます」 | 何をするか具体の動作で言う |
| 環境依存アンカー | 判定質問「見出しへの参照が特定ツール (GitHub/esa 等) 依存の自動アンカーになっているか」→ yes ならヒット | プレーン文字参照 (「手順 3」等) へ |
| 設計背景メタの混在 | 判定質問「他社比較・設計自賛・版の意思決定背景など、運用者ではなく設計レビュアー向けの情報が本文に混ざっているか」→ yes ならヒット。**実例**: 目標設定・自己評価ドラフトの「設計方針」節 (例: 「質重視」「スローガン直結」「評価者FBの反映」等、自分がどう構築ロジックを立てたかの前口上) でも同型が成立する。提出先が一次/二次考課者である以上、構築ロジックの前口上は提出前に外す (末尾の「面談前に最終調整してください」のような機能的な引き継ぎメモとは区別する — こちらは performative でないため保持) | 別紙・別セクションへ分離し、本文には意図を 1 行に圧縮する |

## 較正実例 (採点軸: 具体性 / 削減 / リズム)

### 実例: 周知 — 意気込みを事実に置き換え、失敗を先回りする

**before** (平均 2.3 → 書き直し):

> 🚀 新ルール導入のお知らせ! この度、経費精算のフローが大きく変わります! チーム一丸となって、より良い運用を目指していきましょう! 皆様のご協力が不可欠です!

採点: 具体性 2 (いつ・誰が・何が変わるか無い) / 削減 2 / リズム 3。機械ゲート 3 ヒット (絵文字・「!」連発・意気込み)。

**after** (平均 8.0):

> 経費精算のフロー変更 (8/1 申請分から)。
> 対象: 全員。変更点: 承認者が課長 → 部長に変わる。
> 8/1 以降に旧フォームで申請すると差し戻しになるので注意。詳細手順: <リンク>。質問は #keihi へ。

採点: 具体性 9 (日付・対象・変更点・失敗条件) / 削減 8 / リズム 7

直した点: 意気込み 4 文を事実 4 点に置換 / 「旧フォームだと差し戻し」という**つまずきの先回り**を追加 — この文書種の人間らしさはここに出る (読み手の作業を想像した者にしか書けない一行)。

## 注意

- 本 module と case-chat の境界: 期日・必須アクションを伴う正式な周知は配信先が Slack でも本 module。雑談的な軽い連絡は case-chat。混在時は本文を本 module、Slack 導入行 (名乗り 1 行) だけ case-chat の作法 (+ 声のプロファイルがあればその register) で書く
- **本人名義でも本文に名乗り・声を入れない** (H6 ✗)。名乗りが要る場面は上記の導入行分離で解決する
- 長い手順書の章構成・見出しは長文向けの見出し規範を別途併用する
- **共有語彙は読み手への想像力の具体例** (確定): 配布先に非エンジニア・他部門が混じる場合、内部符牒・略語は初出に一言展開する (2 回目以降は略記でよい)。H5 (特定の読み手) の具体化の一例
