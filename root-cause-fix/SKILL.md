# Skill: Root Cause Fix

ユーザーの自然言語指示に対して複数回の試行錯誤が発生した場合に、根本原因を特定し再発防止策を講じるワークフロー。

## 起動条件

- 同じ意図の指示を 2 回以上やり直しさせられた場合に **自動的に** このスキルのフローに入る
- ユーザーが「原因分析して再発防止しろ」と明示した場合

## Phase 1: 失敗の認識

以下のシグナルを検知したら即座にこのスキルを発動する:

| シグナル | 例 |
|---------|---|
| 同じ指示の繰り返し | 「まだ直ってない」「変わってない」 |
| 期待と逆の結果 | 「大きくしろと言ったのに小さくなった」 |
| 副作用の発生 | 「横幅変わってるやん」「レイアウト崩れた」 |
| 段階的エスカレーション | 「+4px」「もう+4px」「もう+12px」（3回以上） |

## Phase 2: 原因分析

### 2.1 現状の正確な把握

修正を試みる前に、**必ず**以下を確認する:

1. 対象要素の現在のスタイル値（CSS の cascade を追う）
2. 親要素のレイアウトモデル（flex? grid? block?）
3. 兄弟要素との関係（flex:1 が空間をどう分配しているか）
4. inline style の有無と CSS クラスとの優先度関係

### 2.2 仮説の立案

修正が効かなかった場合、以下の観点で原因を分類する:

| 原因カテゴリ | 典型例 |
|------------|--------|
| セレクタ不一致 | クラスが変わった / HTML 構造が変わった |
| 優先度負け | inline style > class / !important の有無 |
| レイアウトモデルの誤解 | flex:1 が空間吸収 / margin collapse |
| 値の単位・方向の誤り | padding vs margin / top vs bottom |
| 副作用の見落とし | 変更 A が変更 B に影響している |

### 2.3 検証

仮説を立てたら、**修正を適用する前に**ユーザーに原因と修正方針を1文で説明する。

## Phase 3: 修正の実行

### 3.1 影響範囲の限定

- 修正は対象箇所のみに閉じる。他の要素に影響しないことを確認する
- 複数箇所を同時に変更しない。1つ変えて結果を確認する（ツール設定の追加・試用でも同じ。変更前の状態に戻せることを確認してから 1 つずつ試す）

### 3.2 修正後の検証項目

- 対象要素: 意図通りに変わったか？
- 隣接要素: 副作用が出ていないか？
- 別スライド: 共通 CSS を変えた場合、他スライドに影響しないか？

## Phase 4: 再発防止

修正完了後、以下を実行する:

1. **原因を1文で記述**: 何が問題だったか（例:「flex:1 の外に移動したため margin-top が効かなくなった」）
2. **反映先の判定**: 技術的な gotcha（ハマりどころ）はコードのコメントやデザインシステム・スタイルガイドのドキュメントに追記し、行動規範やプロセス上の教訓はプロジェクトの指示ファイルや運用ドキュメントに追記する
3. **反映の実行**: 再発防止策を適切なファイルに追記する

## アンチパターン（このスキルでやってはいけないこと）

- 原因を分析せずに値を変えて「試す」（トライ＆エラー禁止）
- 「計算上は正しいはず」で押し通す（見た目が正義）
- 副作用を無視して「対象箇所だけ直った」で完了とする
- 何でも memory に書く（技術的 gotcha はコードベースに残す）
